Декомпозиция

Декомпозицию можно рассматривать как основу модульной архитектуры.

Все проекты должны быть максимально декомпозированы, что даст возможность:

  • Легко изменять отдельные части системы.
  • Контролировать взаимосвязи в системе. Если у системы всё со всем связано — такое отслеживать почти невозможно или крайне проблематично.

Рассмотрим принципы правильной декомпозиции.

Иерархичность

Программная система должна быть разбита на небольшие «атомарные» подсистемы. Каждая из них решает чётко поставленную перед ней подзадачу.

Сами подсистемы разбивают на компоненты, которые при взаимодействии решают поставленную задачу. Компонентом может быть класс, модуль или функция.

Функциональность

Главный инструмент при реализации функциональности — паттерн «Модуль». Он уже был рассмотрен в теме про модули.

Кратко повторим: модуль — это функция и данные, необходимые для её выполнения. Модуль атомарен. Некоторые его свойства:

  • Инкапсуляция данных;
  • Управление зависимостями (создание структуры подключаемых данных);
  • Не засоряет глобальный контекст приложения.

С точки зрения JavaScript небольшой пример, который резюмирует поведение паттерна «Модуль»:

(function (args, modules) {
	// Локальные переменные
  const dataFirst = ... ; 
	const dataSecond = ... ;

	// Импортируется модуль
  const Base = modules.Base;

  class Module extends Base {
    constructor () { ... }

    do () {
        console.log(dataFirst, dataSecond);
    }
  }

	// Экспортируется модуль
  modules.Module = Module;
})(args, window.___all_modules);

// Использование
const Module = window.Module;
const m1 = new Module();
const m2 = new Module();
 
m1.do();

Отличная статья про «Эволюцию модульного JavaScript». Основные способы: IIFE, CommonJS, AMD, UMD, ES2015 Modules.

Основные принципы написания:

  • Один файл — один модуль. Если появилась необходимость определить в одном файле несколько модулей — вы явно делаете что-то не так.
  • Не допускайте циклических зависимостей.
  • Не создавайте большие модули с множеством экспортируемых функций. Можно создавать множество небольших «атомарных» функций модулей.

Слабая связность

Модули, полученные в результате декомпозиции, должны быть сопряжены внутри составных частей модуля и почти не связаны.

По сути, они должны быть независимы, но иметь возможность взаимодействовать без знаний друг о друге и устройстве внутренностей каждого модуля.

Вопросы, которые помогут сделать слабосвязную архитектуру:

  • Какую проблему решает модуль?
  • Легко ли покрыть его тестами?
  • Возможно ли использовать модуль самостоятельно или в другом окружении?
  • Как сильно изменения в одном модуле отразятся на остальных?

Способы снижения связанности модулей:

  • Использовать паттерны ООП;
  • Применять закон Деметры (law of Demeter) — запрет неявных и транзитивных зависимостей;
  • Применять композицию вместо наследования там, где это необходимо. Как правильно это сделать — покажем дальше в уроке.

В качестве примера реализуем паттерн «Наблюдатель» (англ. Observable). Он позволяет применять следующий подход:

Вы заходите на сайт и подписываетесь на обновления через почту. После этого сервис уведомляет вас по почте обо всех новинках и изменениях.

Формальным языком — паттерн позволяет реализовать систему подписок, когда все причастные подписываются на некоторое событие и получают уведомления об изменениях.

В качестве примера приведём реализацию паттерна, и как она поможет сделать код менее связанным:

class Service {
	// Подписка на события
  on(event, callback) {
    this.listeners[event].push(callback);
  }

	// Отписка от события
  off(event, callback) { 
    this.listeners[event] = this.listeners[event]
        .filter(listener => listener !== callback);
  }

	// Публикуем событие (ещё говорят — диспатчим, эмитим)
  emit(event, data) {
    this.listeners[event].forEach(function (listener) {
        listener(data);
    });
  }
}

const service = new Service();

// Функция-обработчик события
const onLoad = function (data) { 
	console.log(data); 
}
 
// Подписываемся на событие
service.on('ended', onLoad);

service.emit('ended', {data: 42});    // событие 1
service.emit('ended', {foo: 'bar'});  // событие 2

// Отписываемся от события
service.off('ended', onLoad);

Сравним, как можно получить данные о пользователе и обновить отображение без применения паттерна «Наблюдатель»:

// services/user-service.js
class UserService {
  auth(login, password) {
    return HTTP.post('/api', {login, password})
      .then(function (user) {
        this.user = user;

        this.chatsSection.reRender();
        this.signupSection.hide();
        this.profileSection.show(user);
    }.bind(this));
  }
}

// blocks/profile.js
const UserService = window.services.UserService;
 
class ProfileBlock {
  constructor () {
    this.userService = new UserService();
  }
 
  render(login, password) {
    const user = this.userService.getUser();
    this.el.innerHTML = templator({user});
  }
}

Есть более гибкий и расширяемый подход — использовать так называемый “Event Bus”. Это синоним механизма «Наблюдатель», который был реализован выше. Вот так может получиться, когда мы убираем явную связанность сервиса и блока:

// services/user-service.js

class UserService {
  auth (login, password) {
    return HTTP.POST('/api', {login, password})
      .then(function (user) {
        this.user = user;
        this.emit('signed', user);
    }.bind(this));
  }

  on(event, callback) { ... }
  emit(eventName, eventData) { ... }
}

// blocks/profile.js
class ProfileBlock {
  onUserLoaded(user) {
    this.el.innerHTML = templator({users: users});
  }
}

// main.js
UserService.on('chats-loaded', chatsSection.reRender.bind(chatsSection));
UserService.on('user-loaded', profileBlock.onUserLoaded.bind(profileBlock));

UserService.auth('login', 'password');

Основные преимущества подобного подхода:

  • Все “Observable” модули реализуют один и тот же интерфейс методов;
  • Модули, на которые подписываемся, — сами знают, когда и какие события эмитить;
  • Модули, которые подписываются, — сами знают, как и когда обрабатывать такие события;
  • Каждая из сторон ничего не знает друг о друге (модулям известны только названия события и формат сообщений);
  • Удобно оповещать систему о новых событиях.

В случае, если подобных “Observable” модулей много, код дублируется:

// services/user-service.js
class UserService {
  // ...

  on(event, callback) { ... }
  emit(eventName, eventData) { ... }
}

// services/chats-service.js
class ChatsService {
  // ...

  on(event, callback) { ... }
  emit(eventName, eventData) { ... }
}

Оба сервиса имеют идентичные методы on, emit и подобные для работы с подписками.

Одно из решений — отделить общие методы в отдельный модуль, и наследоваться от него.

// services/utils/observable.js
class Observable {
  on(event, callback) { ... }
  emit(eventName, eventData) { ... }
}

// services/user-service.js
class UserService extends Observable {
  // ...

  on(event, callback) { ... }
  emit(eventName, eventData) { ... }
}

// services/chats-service.js
class ChatsService extends Observable {
  // ...

  // on(event, callback) { ... } — уже не нужны
  // emit(eventName, eventData) { ... } — уже не нужны
}

Паттерн «Миксин»

Миксины помогают решить проблему множественного наследования. Отличаются от интерфейсов тем, что уже содержат готовый функционал, а не описание спецификации.

Почитать подробнее про примеси можно на Хабре или в «Современном учебнике JavaScript».

Формализованным языком, примесь (англ. mixin) — это класс или объект, реализующий выделенное поведение. Используется для уточнения поведения других классов и не предназначен для самостоятельного использования.

const ObservableMixin = {
  on(event, callback) { ... }
  emit(eventName, eventData) { ... }
  // ...
}

class UserService {
  constructor () {
    this.emit('event', { ... });
  }
}

Object.assign(UserService.prototype, ObservableMixin);

Что кроме наследования?

Возьмём автомобиль. У него есть колёса, двигатель, двери, корпус (кузов). Описать каждую сущность можно так:

class Engine {
	start() { /*...*/ }
}

class Wheel {
	rotate() { /*...*/ }
}

class Door {
	open() { /*...*/ }
}

class Body {
	clear() { /*...*/ }
}

При создании класса, который описывает автомобиль, — будет некорректно наследоваться от двигателя, колеса или двери. Всё потому, что эти сущности — лишь составные части и не описывают общее поведение машины.

В этом случае правильно использовать не наследование, а композицию.

class Car {
	constructor() {
		this.engine = new Engine();
		this.body = new Body();
		this.wheels = new Array(4).map(_ => new Wheel());
		// ...
	}
}

Теперь автомобиль — это именно сконструированная сущность.

Снова возникает вопрос — что произойдёт, если таких модулей будет много?

Медиатор

Если в системе существует большое количество модулей, их прямое взаимодействие друг с другом становится всё сложнее и сложнее. Даже несмотря на применение Event Bus.

Именно поэтому стоит заменить взаимодействие «все со всеми» на «один со всеми»:

// modules/event-bus.js
export default class EventBus {
  on(event, callback) { ... }
  off(event, callback) { ... }
  emit(eventName, eventData) { ... }
}
 
// main.js
import EventBus from './modules/event-bus.js';
window.bus = new EventBus();

// services/user-service.js
export default class UserService {
	login () {
	  HTTP.post({ ... })
    .then(function (user) {
      // do stuff
          
      window.bus.emit('user:logged-in', user);
    })
  }
}

// blocks/user-profile.js
export default class UserProfile {
  constructor () {
    window.bus.on('user:logged-in', function (user) {
      // do stuff
        
      this.render();
    }.bind(this))
  }
}

Использовать глобальные переменные — очень плохо, поскольку нельзя контролировать, когда они перезапишутся и перезапишутся ли. Как итог — нельзя быть уверенным, что глобальная переменная в текущий момент содержит актуальную ссылку на ожидаемый ресурс.

Как решить такую проблему? Модульность и паттерн «Синглтон». Он позволяет создавать только один инстанс класса на весь проект:

// modules/event-bus.js
class EventBus {
  on(event, callback) { ... }
  off(event, callback) { ... }
  emit(eventName, eventData) { ... }
}
 
export default new EventBus();

(function (global) {
	function Singleton() {
		let instance = this,
				prototype = Singleton.prototype;
		
		Singleton = function() {
			return instance;
		}
	
		Singleton.prototype = prototype;
		Singleton.constructor = Singleton;
		instance.constructor = Singleton;
	
		return instance;
	}

	firstSingleton = new Singleton;
	Singleton.prototype.newProperty = true;
	secondSingleton = new Singleton;
})(this);

Задачи паттерна «Синглтон»:

  • Ограничить количество экземпляров класса одним;
  • При повторном вызове конструктора возвращать ссылку на созданный ранее экземпляр класса.

Применять паттерн можно вот так:

// blocks/user-profile.js
import bus from '../modules/event-bus.js';
 
export default class UserProfile {
  constructor() {
    bus.on('user:logged-in', function (user) {
      // do stuff
      
      this.render();
    }.bind(this))
  }
}

Есть ещё способы для реализации «Синглтона». Например, через класс и статическое свойство класса:

// modules/event-bus.js
export default class EventBus {
  constructor() {
    if (EventBus.__instance) {
      return EventBus.__instance;
    }

    // Логика инициализации
    EventBus.__instance = this;
  }
}

Теперь можно сравнить ссылки:

// main.js
import EventBus from './modules/event-bus.js';
 
const bus1 = new EventBus();
const bus2 = new EventBus();
 
bus1 === bus2; // true

Итоги

Резюме для реализации композиции в ваших проектах:

  • Минимизировать использование глобальных зависимостей.
  • Не использовать неявные зависимости — все зависимости модуля должны быть явно прописаны.
  • Минимизировать связи между модулями. В помощь — «Наблюдатель», «Медиатор».
