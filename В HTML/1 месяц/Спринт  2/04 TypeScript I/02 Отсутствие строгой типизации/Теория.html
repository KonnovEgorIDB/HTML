Отсутствие строгой типизации

Рассмотрим простейшую функцию суммирования двух аргументов:

function sum(a, b) {
  return a + b;
}

В зависимости от типов данных a и b, функция возвращает разные значения, что не всегда даёт желаемый результат:

sum(2, 2); // 4
sum(2, '2'); // '22'
sum([], []); // ''
sum([], {}); // '[object Object]'
sum({}, []); // 0

Если разработчики не приучены к написанию тестов, неочевидные результаты или ошибки будут попадаться постоянно. Пострадают и пользователи приложения, и репутация команды.

Тесты помогают, но ценой усложнения кода:

function sum(a, b) {
  if (typeof a !== 'number' || typeof b !== 'number') {
    throw new Error('a and b must be a numbers');
  }

  return a + b;
}

Вместо одной простой строчки получаются дополнительные громоздкие строки с явной проверкой типов. И здесь возникают новые проблемы:

  • все ли типы проверили,
  • нет ли ошибок в самой проверке,
  • следует описать JSDoc.

Изменения в коде

Представьте ситуацию, бэкэнд в ответ на некоторый запрос пообещал вам, как разработчику фронта, возвращать подобный объект:

{
	id: 'fe672dc7-fff2-4f20-b2bf-7062a6d33a9a',
	title: 'Товар 1',
	cost: 500,
	currency: '₽',
}

Идёт время, многие части приложения завязываются на эту структуру данных и начинают работать с полями cost и currency, например, конкатенируя их для отображения на экране. Но в какой-то момент бэкенд решает: «Если товар отсутствует на складе — вернём null в полях cost и currency». Ситуация выдуманная, но и такое бывает.

Что должен в такой ситуации сделать разработчик фронтенда? Пройтись по всем местам, где использовались эти поля (а их ещё нужно найти) и добавить там условие if (cost !== null && currency !== null).... Неприятная и нудная работа.

Конечно, с подобными ситуациям можно бороться введением геттера verboseCost, но если у вас недостаточно опыта — вы пока можете не уметь прогнозировать такие «подставы». Хотелось бы при обнаружении такого неприятного изменения сделать небольшую правку, чтобы машина при этом сама указала, где в программе использовались эти поля, и что появилась опасность в связи с возможным значением null. Строгая типизация помогает с таким автоматическим обнаружением опасностей.

Стоимость ошибки

Небольшие ошибки в типах данных ведут к масштабным проблемам:

  • Крупная авиакомпания понесла миллионные убытки из-за ошибки вида x is not a function при расчёте стоимости билетов.
  • Логистическая компания не раз получала задание доставить груз в Гвинейский залив по координатам [0, 0]. Всё из-за неявного преобразования undefined.

Этих ошибок можно было избежать валидацией и правильной обработкой типов.

Итого

Основные проблемы:

  • Неявные преобразования;
  • Типы становятся известны в runtime.
