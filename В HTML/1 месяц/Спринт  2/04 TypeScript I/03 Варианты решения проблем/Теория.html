Варианты решения проблем

Кроме JavaScript существует большое число различных надстроек над языком и других компилируемых в машинный код ЯП для браузеров.

Подробно рассматривать аналоги не будем, но для знания о существовании каждого из них — ниже приведём самые популярные примеры.

Полифиллы

Можно писать собственные реализации той или иной фичи стандарта. Пример:

if (!Object.is) {
	Object.is = function(x, y) {
	  if (x === y) { 
			return x !== 0 || 1 / x === 1 / y; 
		}
	  else { 
			return x !== x && y !== y; 
		}
	}
}

Проблема: заново написать все стандарты и покрыть их тестами — это займёт много времени. И всё так же нет типов, придётся проверять их вручную.

На самом деле все полифилы давно написаны за нас, и можно их поставить из npm. Но если бездумно ставить полифилы — вес приложения может заметно вырасти.

Транспиляция из ES.Next

С помощью специальных компиляторов можно преобразовывать современный код в более старый и поддерживаемый различными ранними версиями браузеров, набор которых можно указать при конфигурации. Например: «компилируй современный JS в более старый JS, который бы поддерживался в IE8+». Пример такого компилятора — Babel. На его сайте есть playground, где можно посмотреть, как инструмент компилирует современный код под различные версии и настройки.

Babel обладает плагинной системой, которая позволяет настроить компилятор так, как он должен работать под ваших пользователей. Примеры:

  • arrow-functions,
  • classes,
  • destructuring,
  • duplicate-keys,
  • for-of.
import { decorator } from 'lib';

class ChatBase {
	constructor({ name, ...rest}) {
		console.log(`Привет, ${name}, твои свойства:`, rest);
	}
}

@decorator
class Chats extends ChatBase {
	async *doSmth(...staff) {
		// something...
	}
}

Проблема: Ура! Можно использовать последние стандарты и компилировать их под нужные браузеры. Но всё так же нет типизации.

Отдельные языки со своими компиляторами

Языки вроде Dart, CoffeeScript, Clojure и Elm в целом неплохие, но основная проблема — это не «родной» JavaScript. Читаемость кода упадёт, переключаться будет сложнее, всплывут вопросы с поддержкой и интеграцией, а зоопарк различного фронтенда будет только мешать. Даже с типизацией и многими крутыми вещами «из коробки».

Для примера приведены сниппеты кода подобных языков:

Dart

import 'dart:async';
import 'dart:math' show Random;
 
Stream<double> computePi({int batch: 1000000}) async* { ... }
 
main() async {
  print('Compute π using the Monte Carlo method.');
  await for (var estimate in computePi()) {
    print('π ≅ $estimate');
  }
}

CoffeeScript

class Animal
  constructor: (@name) ->

  move: (meters) ->
    alert @name + " moved #{meters}m."

class Snake extends Animal
  move: ->
    alert "Slithering..."
    super 5

sam = new Snake "Sammy the Python"

sam.move()

(set! *main-cli-fn* -main)

Elm

import Html exposing (text)
 
main =
  text (toString (zip ["Tom", "Sue", "Bob"] [45, 31, 26]))
 
zip : List a -> List b -> List (a,b)
zip xs ys =
  case (xs, ys) of
	( x :: xBack, y :: yBack ) ->
		(x,y) :: zip xBack yBack
 
	(_, _) ->
		[]

Типизированный JS

Flowjs

Инструмент позволяет начать покрывать типами JS-код прямо сейчас, без регистрации и смс. Не нужно переписывать весь проект, достаточно комментариями показывать, какие файлы нужно начать обрабатывать с типизацией.

// @flow
function square(n: number): number {
  return n * n;
}

square("2"); // Error!

TypeScript

Один из самых популярных инструментов для типизации клиентской части. Имеет более сложную систему обработки типов, местами более гибкую настройку и большую поддержку.

interface Person {
  name: string;
  age: number;
}

function meet(person: Person) {
  return `Привет, я ${person.name}, мне ${person.age}`;
}

const user = { name: "Иннокентий", age: 21 };
console.log(meet(user));

Flow и TypeScript часто сравнивают. У каждого из них есть большие дыры, из-за которых можно даже не полениться написать issue в GitHub, но это всё ещё два очень мощных инструмента.

Их проблема — это хоть и статическая типизация с выводом типов и компиляцией, однако это не полноценный язык со статической типизацией. Существуют места с плохим выводом типов и места, где можно довериться разработчику. Что плохо. Можно сделать так, что их вывод работать не будет, а проект превратится в JS с оверхедом на написание неработающих типов.

«Готовить» подобные вещи нужно осторожно и проверять то, что пишете.
