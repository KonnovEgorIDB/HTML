Дизайн языка

Как и в JS, знание паттернов и лучших практик CSS помогает фронтенд-разработчику. Важно понимать не только как писать стили, но и какие принципы закладывались в инструменты при их создании.

Принципы дизайна CSS

Все версии CSS базируются на общих принципах. Основные из них:

  • Совместимость версий — поздние версии CSS обратно совместимы с ранними. Более того, если клиент поддерживает только устаревшую версию CSS, он сможет отобразить содержимое документа, отбросив незнакомые ему элементы вёрстки.
  • Слабая связанность со структурой HTML — дизайн CSS помогает менять оформление, почти не вмешиваясь в структуру самого документа.
  • Независимость от клиентского устройства — таблицы стилей описаны универсальным образом, понятным разным устройствам и программам — от браузеров до принтеров.
  • Открытость для других языков — дизайн позволяет управлять разметкой как напрямую, так и через сторонние языки. Например, через JavaScript.
  • Удобство поддержки — дизайн помогает выдерживать единый стиль вёрстки для множества документов.
  • Простота — таблицы стилей легко читать и править. Это достигается благодаря независимости свойств CSS. При этом в большинстве случаев каждой задаче соответствует только одно свойство.
  • Гибкость — каскадность языка позволяет применить таблицу стилей множеством способов: через пользовательские стили, ссылки на общую таблицу стилей, отдельные стили для каждого элемента.

Все принципы дизайна CSS описаны в документации W3C.

Как стили попадают на страницу

Перечислим источники, из которых браузер получает правила оформления:

  1. Браузерные стили — default (user agent) style sheet. Их можно переопределять самостоятельно или с помощью библиотек. Например, normalize.css.
  2. Пользовательские стили. Их нельзя не учитывать, равно как не стоит пренебрегать использованием !important.
  3. Ссылка на таблицу стилей: link и rel="stylesheet".
  4. Тег style.
  5. Атрибут style — этот метод часто используется вместе с JS.

Написание стилей

Чтобы писать стили, разработчик должен понимать каскадность правил CSS и управлять порядком наложения элементов.

Каскадность CSS позволяет создавать правила любой степени вложенности:

*                                  /* универсальный селектор */
div, span, a                       /* селекторы по имени тегов */
.class                             /* селекторы по имени классов */
#id                                /* селекторы по идентификаторам */
[type="text"], [src*="/img/"]      /* селекторы по атрибутам */
:first-child, :visited, :nth-of-type(An+B), :empty ... 
::before, ::placeholder, ::selection, ::first-letter ... 
a > a, a + a , a ~ a               /* вложенность и каскадирование */

Дополнительные материалы о селекторах:

  • Документация MDN;
  • Хабр: «Взвешиваем селекторы CSS»;
  • Калькулятор специфичности селектора.

За порядок наложения элементов отвечает свойство z-index. Если два элемента накладываются друг на друга, то сверху отобразится элемент с более высоким индексом.

Чтобы навести порядок в наложении элементов, используйте следующие правила:

  1. 0000–1999: основной контент,
  2. 2000–2999: выпадающие списки,
  3. 3000–3999: навигация,
  4. 4000–4999: шапка и подвал,
  5. 5000–7999: другое,
  6. 8000–8999: модальные окна,
  7. 9000–9999: уведомления.

Проблемы со стилями

Рассмотрим задачи, которые помогут выявить проблемы при написании стилей.

Задача. Один и тот же компонент должен выглядеть по-разному в зависимости от блока или страницы:

Решение. У одинаковых компонентов будут разные родители. Тогда именно к родителю следует привязать стиль:

/* Изменение компонентов в зависимости от родителя */
.button { border: 1px solid black; }
#sidebar .button { border-color: red; }
#header .button { border-color: green; }
#menu .button { border-color: blue; }

Проблема: такой код сложно переиспользовать, сложно искать в проекте и сложно изменять. В результате, когда одинаковые стили понадобятся в разных разделах, придётся:

  • либо лишний раз копировать один и тот же код,
  • либо отказаться от консистентного обозначения id и давать одинаковые имена разнородным элементам.

Задача. Найти элемент на странице, обходя DOM-элементы, — про такой способ говорят «вслепую».

Решение. Придётся привязать стили к конкретным элементам HTML:

#main-nav ul li ul li ol span div { ... }
#content .article h1:first-child [name=accent] { ... }
#sidebar > div > h3 + p a ~ strong { ... }

Проблема: нарушается один из принципов дизайна CSS — стили сильно привязаны к структуре документа. Любое добавление нового элемента или изменение структуры сломает стили. Поддержка такого оформления отнимет много сил.

Задача. Упростить чтение правил.

Решение. Под влиянием библиотеки Bootstrap классам часто дают распространённые имена:

/* Широко используемые имена классов */
.article { ... }
.article .header { ... }
.article .title { ... }
.article .content { ... }
.article .section { ... }

Проблема: высокая вероятность пересечения имён с внешними библиотеками внутри собственного проекта или компонента.

Суперклассы

Одним из частых кейсов был «суперкласс», который решал определённые проблемы и содержал в себе всю возможную логику: Сейчас он тоже встречается, но с приходом паттернов всё реже.

/* Супер класс! */
.super-class {
  margin: 10px;
  position: absolute;
  background: black;
  color: white;
  transition: color 0.2s;
  .....
}

Компонентный подход легко применяется к CSS. Он важен, поскольку в большом проекте вы не сможете делать небольшие атомарные изменения в стилях. Даже самые маленькие правки повлекут большие изменения во всём проекте.

Хорошая архитектура

Все архитектурные рекомендации для JavaScript верны и для CSS:

  • поддержка — все в команде знают и понимают, как писать стили;
  • избегайте повторного использования — следуйте принципу DRY;
  • помните о масштабируемости, ведь небольшое изменение стилей потребует пересмотра большого количества кода и может стать причиной проблем.
