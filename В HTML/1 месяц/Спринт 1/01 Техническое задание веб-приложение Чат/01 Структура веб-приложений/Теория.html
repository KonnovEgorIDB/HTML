Структура веб-приложений

Когда фронтенд только зарождался, всё было относительно просто. С веб-сервера приходили сгенерированные HTML-страницы и пачка таких страниц называлась сайтом. Они оживлялись небольшим количеством JS и CSS, а люди были сосредоточены на их наполнении контентом.

Время шло, интерфейсы становились все сложнее и интерактивнее и в 2000-x начали появляться первые фреймворки и библиотеки для построения уже веб-приложений. Приложений, которые могут работать без перезагрузки страницы, прямо в браузере динамически формировать новые страницы и хранить состояние пользователя почти как нативные десктопные или мобильные программы.

Если интересно больше узнать об истории JS-фреймворков, обратите внимание на статью Дмитрия Чудинова в блоге Яндекс.Практикума на Хабре.

Сегодня даже маленькие приложения начинают писать на React + Redux + Webpack + (добавьте свои любимые технологии). С одной стороны, это правильно, фронтенд как направление растёт очень быстро и уже сейчас стал довольно сложным. С другой — а почему нельзя написать всё с нуля? Почему нельзя написать небольшие приложения без сборщиков, JSX и кучи библиотек в package.json?

Для того чтобы лучше понять, зачем нужны фреймворки и библиотеки, можно попробовать написать небольшое SPA (Single page application) без их использования. Этим вы, кстати, и займётесь в этом модуле.

В процессе разработки такого приложения можно собрать огромное количество проблем и, как ни странно, опыта и понимания, из каких же частей состоит современное веб-приложение и как работает всё под капотом. Но прежде чем приступать к разработке такого приложения, нужно определиться, из каких частей оно вообще состоит. Можете несколько минут подумать над этим сами, а дальше сравнить их с пунктами ниже.

Окружение для разработки и структура проекта

Работать на медленном ноутбуке, за качающимся столом и сидя на стуле без спинки не очень удобно. А если быть точнее, то совсем. Так же и с проектами, без удобных инструментов и структуры совсем не удобно. Поэтому любой проект начинается с разработки каркаса приложения и настройки первичного окружения.

Выбор инструментов зависит от особенностей проекта и предпочтений команды, но нужно позаботиться о линтинге кода (ESLint, Stylelint), автоматическом форматировании (Prettier) и сборке (Webpack или Parcel).

Структура проекта обычно делится на несколько директорий внутри src (с англ “source”, исходник): компоненты, страницы (тоже компоненты), утилиты:

src/
  api/*
  components/*
  pages/*
  utils/*
  index.ts
  index.css

Каждый компонент содержит в себе представление, стили, тесты и другие файлы (например, SVG-картинки), которые относятся к нему.

src/components/
  Message/
    Message.ts
    Message.css
    Message.test.ts

На больших проектах добавляют разделение структуры на основе модулей или «фич» (feature based development). В таком случае в рамках одного модуля могут быть свои компоненты и страницы, они объединены бизнес-логикой проекта. Например, в проекте есть авторизация и дашборд администратора. Файловая структура может выглядеть следующим образом:

src/features
  auth/
		api/*
		components/*
    pages/
      RegisterPage.ts
			LoginPage.ts
		utils/*
  dashboard/
		components/*
		pages/
			DashboardPage.ts

Тесты в проекте удобно размещать рядом с тестируемыми файлами, чтобы не приходилось их искать по проекту (пример выше с компонентом Message).

Интерфейс (Interface)

В приложениях часто забывают или не уделяют внимания визуальной составляющей интерфейса, то есть вёрстке. Из двух плюс-минус одинаковых проектов пользователи будут выбирать тот, которым удобно пользоваться, где есть мобильная версия и красивый дизайн.

Есть много инструментов для проектирования UI (например, Figma) и сайтов, на которых ежедневно выкладывают различные интерфейсы (например, Dribbble). Ими можно вдохновляться для своих нужд.

А ещё есть множество готовых дизайн-систем и компонентов, которые довольно просто подключить и использовать у себя, если нет требования придумать дизайн с нуля (например, Bulma, Ant Design или Bootstrap).

Обратите внимание, что использовать дизайн-системы в первом модуле нельзя, то есть компоненты нужно будет сделать самостоятельно.

Представление (View)

Одна из самых важных частей приложения — это движок для рендеринга. Он отвечает за генерацию DOM-дерева (шаблонизатор) из атомарных компонентов, вставку этого дерева на итоговую страницу и его обновление при изменениях. Раньше с помощью обычного шаблонизатора формировался HTML и вставлялся на страницу (например, в Backbone, одном из первых фронтенд фреймворков). Но при таком подходе есть несколько проблем. Первая: сложность при работе с локальным состоянием компонентов и системой событий (обработка кликов на кнопки, ввод текста в инпуте). Вторая: в производительности. Даже небольшие проекты начинали тормозить. Почему? Потому что самая дорогая операция при работе с DOM-деревом — это его обновление.

Поэтому появилось понятие виртуального DOM. Это представление пользовательского интерфейса в памяти (например, в JavaScript-переменной), по которому можно сформировать настоящее DOM-дерево. Помимо формирования, виртуальный DOM отвечает за синхронизацию с реальным DOM.

Например, у нас есть следующий код:

<div id="app">
 Hello world
</div>

Виртуальное представление может выглядеть следующим образом:

const vNode = {
  tagName: "div",
  props: {
    id: "app"
  },
  children: [
    "Hello world"
  ],
}

Такой паттерн позволяет описывать интерфейсы в декларативном подходе, абстрагирует от прямой работы с DOM, обработчиками событий и атрибутов и оптимизирует работу обновления только нужных частей DOM-дерева (отвечает за синхронизацию с реальным DOM). Но он также сложен в реализации.

Если хотите самостоятельно реализовать виртуальное дерево, вам поможет статья «Как написать свой Virtual DOM» с пошаговой инструкцией.

Также есть много небольших репозиториев на Github, которые предоставляют готовые реализации. Например, библиотека superfine предоставляет свою реализацию Virtual DOM в 300 строк кода и умеет работать с ключами в списках (если писали на React, то знаете о явном указании key в массивах), обрабатывать SVG, выполняться на стороне сервера и многое другое.

Для своего проекта можно использовать как обычный шаблонизатор, так и попробовать самому реализовать VDOM.

Состояние (State)

В SPA нужно где-то хранить состояние приложения (информацию о пользователе, о данных, введённых в текстовые поля, о загруженных бизнес-сущностях). В самой простой реализации состояние можно хранить в обычном JavaScript объекте в памяти открытой страницы.

Но, помимо хранилища, в определение состояния входит data flow ******(поток данных), которое определяет, как состояние будет обновляться. Существует два популярных способа работы с данными: one-way data binding **(с англ. — одностороннее связывание данных) и **two-way data binding **(с англ. — двустороннее связывание данных).

One-way data binding можно представить в виде бесконечного цикла, в котором пользователь (или любые другие события, например, веб-сокет или таймер) обновляют состояние, а после все подписанные источники (например, ваше представление) обновляются. То есть получаем однонаправленный поток данных (обновляется состояния — обновляется представление). Данный подход реализован в Redux, Vuex и многих других библиотеках.

Реализовать такой подход несложно. В простом случае можно на каждое обновление состояния перерисовывать всё приложение:

store.onChange = (store) => {
    renderApp(store);
};

Другой же поход, two-way data binding, связывает две части состояния (внутри хранилища и внутри представления), образуя двухстороннюю связь.

Например, при такой схеме можно менять значение инпута, и будет обновляться значение в хранилище, а можно, наоборот, изменить значение в хранилище, и оно изменится в представлении. Такой подход используется в Angular, он удобен в использовании, но для реализации требуется более сложная структура, чтобы поддержать иллюзию одного состояния. Также могут возникнуть проблемы с производительностью (проблемы были в первом Angular).

На сегодняшний день есть огромное количество различных решений для работы с состоянием, поэтому при необходимости есть из чего выбрать.

Роутинг (Navigation)

Если у приложения больше одной страницы, то необходимо интегрировать навигацию между ними. Может возникнуть вопрос, а зачем вообще нужен роутинг, почему нельзя писать код без навигации? Это можно сделать. Для этого необходимо хранить активную страницу в состоянии приложения и никаких ограничений не возникнет, кроме одной проблемы.

Эта проблема заключается в коварной кнопке «Назад» в браузере. С точки зрения пользователя, в браузере открывается страница с контентом, и ему не важно, как она спроектирована, сайт ли это, SPA или что-то ещё. Ему важно, чтобы при нажатии на кнопку «Назад» (а также «Вперёд» или «Обновить», раз уж зашла речь об этом) он перемещался по приложению, используя историю посещения страниц, а не был выброшен из веб-приложения.

У React, Angular и Vue есть свои встроенные или внешние решения для организации роутинга. Все они основаны на History API — браузерном API для работы с историей текущей сессии страницы через объект window.history. Он предоставляет методы и свойства, которые позволяют переходить «Назад» и «Вперёд» по истории пользователя и подписываться на её изменения (например, когда пользователь вручную меняет URL-страницы).

Реализовать навигацию лучше через шаблон проектирования «Посредник» (Mediator), который позволит не связывать страницы между собой и переключать их через специально выделенный для этого объект (Router). Он хранит информацию о всех страницах, слушает изменения URL и показывает активную страницу.

Публичный интерфейс объекта Router может выглядеть следующим образом:

const router = new Router();

router.use('/home', () => showHomePage());
router.use('/about', () => showAboutPage());

router.go('/home');

Часто роутинг связывают с состоянием приложения, то есть роутинг отвечает только за переключение страниц и слушает события её изменения. А за хранение активной страницы отвечает Store приложения.

Что получается в итоге

Разработка любого приложения начинается с подготовки окружения, сборки и каркаса. Далее ведётся работа над самим приложением (дизайн, представление, состояние, роутинг). Для того чтобы лучше понять каждую из частей, можно попробовать разработать небольшое приложения без использования библиотек и фреймворков для одной из частей или всех сразу.

В реальных проектах, в зависимости от выбранного решения, предоставляются библиотеки для каждой из частей, поэтому самому реализовывать их, скорее всего, не понадобится.
