Рекомендации по SSR

Server Side Rendering — это большая и сложная тема, которой в этом спринте уделяется много времени. В теории описан путь его внедрения на примере. Крайне рекомендуем ознакомиться, прежде чем внедрять SSR в свой проект.

И несколько советов:

  • Сначала нужно формировать стейт и только после рендерить React-приложение. Это нужно, чтобы получить на сервере «слепок приложения» за один рендер.
  • У каждой библиотеки для работы с сайд-эффектами свои подходы к работе на сервере. Например, в Redux Thunk достаточно просто задиспатчить асинхронный экшен, а в Redux Saga нужно вручную запустить сагу, и после выполнения экшенов, также вручную завершить её выполнение.
  • Для различных ассетов при серверной сборке можно использовать null-loader, который просто не будет обрабатывать указанные модули.

Чеклист для самопроверки

  1. Темизация настроена и работает корректно:
    • Переключение делается через «ручки» на NodeJS.
    • Переключить тему может любой: авторизованный или не авторизованный пользователь.
    • Есть минимум две темы, которые отличаются стилями на клиенте.
    • Стили переключаются мгновенно и без перезагрузки страницы.
    • Для хранения тем используется база данных PostgreSQL версии 12+.
    • В таблице темы привязаны к пользователю.
    • Используется корректный (или корректные) индексы для ваших таблиц.
    • Не используются подзапросы в SQL-запросах (если не можете объяснить, зачем они и почему JOIN не решит вашу проблему быстрее).
  2. Форум корректно работает:
    • Должна быть возможность создавать топик, писать комментарии к топику, отвечать на комментарии комментарием (дерево комментариев).
    • Форум должен быть доступен только для авторизованных пользователей.
      1. На NodeJS необходимо возвращать 403-й код ответа, если пользователь не авторизован.
      2. На клиенте необходимо поставить заглушку с переходом на авторизацию (либо не показывать форум вообще, пока пользователь не авторизован).
    • При написании комментария нужно добавить минимум одно дополнительное действие с текстом. Например, возможность выбирать emoji из интерфейса.
  3. Общие требования к NodeJS.
    • Сервер и базы должны быть «обёрнуты» в Docker.
    • Между сервисами в docker-compose (если запускается через него) должны быть корректные зависимости (например, сервис А стартует перед сервисом Б).
    • Должен быть мидлвар для проверки авторизации пользователя через общее API. Мидлвар должен «пробрасываться» к «ручкам» через специальный аргумент app.method(url, [...middlewares], handler).
    • Все сущности для БД должны быть разбиты на отдельные сервисы. Контроллер (хендлер роута в NodeJS) должен отвечать только за бизнес-логику «ручки».
    • Токены и доступы к базам и третьим сервисам не должны находиться в репозитории (можно только если это тестовые данные для входа в локальных системах).
    • Явки / пароли должны добавляться в проект через env.

Рекомендации, которые не стоит игнорировать

  1. Не дублируйте логику. Выносите повторяющуюся логику по сущности в отдельный общий сервис.

  2. Не делайте сервис-космолёт. Сервис не должен уметь всё (ещё и готовить завтрак по утрам). Сервис должен делать только относительно атомарные вещи. Например, обработать и записать в базу или отправить запрос. Сервис не должен полностью преобразовывать данные перед отправкой. Он должен только валидировать и отправлять. Подготавливать данные — дело контроллера (хендлера роута). Ведь везде формат может быть разный.

  3. Не делайте «макаронные» связи или «копипасты» сервисов. Применяйте паттерн Медиатор для устранения лишних связей. Активно пользуйтесь фабриками, если один и тот же сервис не хочется раздувать, но нужно сделать «копию».

  4. Используйте масштабирование процессов в NodeJS. Даже без кластеризации NodeJS может утереть нос многим Web-серверам. А с кластеризацией — уффф… Берегитесь все! Подробнее можно почитать тут.

  5. Не создавайте все роуты для express-сервера в едином месте. Разбивайте на логические единичные файлы и добавляйте отдельно. Пример:
