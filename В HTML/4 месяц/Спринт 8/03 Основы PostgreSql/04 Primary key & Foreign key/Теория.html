Primary key & Foreign key

Primary key (первичный ключ)

Primary key в таблицах, если говорить по-человечески, служит идентификатором строки с данными. Он уникален, и по нему мы можем различать и легко находить строки.

Если, например, надо связать таблицу сотрудников с таблицей должностей — primary key в таблице должностей подходит для этой цели как нельзя лучше. Создаём в таблице пользователей колонку с именем, например role_id, и в неё будем складывать значения primary key из таблицы должностей.

CREATE TABLE users (
	id SERIAL PRIMARY KEY,
	name VARCHAR(255) NOT NULL,
	role_id integer
);

CREATE TABLE roles (
	id SERIAL PRIMARY KEY,
	value VARCHAR(255) NOT NULL
);

INSERT INTO roles (value) VALUES ('Программист'), ('Менеджер'), ('Директор');

INSERT INTO users (name, role_id) VALUES ('Владимир', 1);
INSERT INTO users (name, role_id) VALUES ('Оксана', 2);

Однако сейчас есть проблема: технически в базе данных колонки users.role_id и roles.id никак не связаны. Если удалить строку из roles, то строки в users никак об этом не узнают, и данные придут в неконсистентное состояние — значение в role_id у какой-нибудь строки есть, а фактически такой строки в roles нет. Ниже разберёмся, как это исправить, но сперва пара слов об индексах.

Индексы

Колонка с primary key индексируется автоматически — это значит, что поиск по данной колонке будет очень быстрым. Если id — это primary key, то запрос SELECT * FROM roles WHERE id = 2 будет иметь сложность O(1).

Если искать по колонке, которая не имеет индекса (SELECT * FROM users WHERE name = 'Оксана'), то движок базы будет перебирать все строки в таблице и искать совпадения. С индексами такого не происходит — при индексах база точно знает, какие строки соответствуют условию поиска.

Внутри индексы можно представить как хэш-таблицу — ключами являются значения индексированной колонки, а значениями — ссылки на строки. В действительности, конечно, индекс не является хэш-таблицей, там всё сильно сложнее, но для объяснения сойдёт.

Foreign key (внешний ключ)

Внешний ключ позволяет явно указать базе данных, что колонки в двух таблицах связаны. Зададим такую связь между users.role_id и roles.id. Но прежде разберёмся с синтаксисом создания внешнего ключа:

[CONSTRAINT fk_name]
FOREIGN KEY(fk_columns) 
REFERENCES parent_table(parent_key_columns)
[ON DELETE delete_action]
[ON UPDATE update_action]
  1. Необязательно — задать имя налагаемого ограничения. За это отвечает CONSTRAINT.
  2. FOREIGN KEY(имя_колонки) — создаём внешний ключ, которым станет указанная в скобках колонка.
  3. REFERENCES внешняя_таблица(имя колонки в ней) — указываем ключу связаться с колонкой в определённой таблице.
  4. Необязательно — действия при обновлении и удалении значения во внешней таблице. Их мы ещё коснёмся дальше.

Теперь изменим структуру таблицы users:

ALTER TABLE users ADD CONSTRAINT roles_fk FOREIGN KEY (role_id) REFERENCES roles (id);
  1. Обновляем таблицу users.
  2. Называем новое ограничение roles_fk.
  3. Делаем колонку role_id внешним ключом.
  4. Она (колонка role_id) связывается с колонкой id из таблицы roles.

Теперь между таблицами есть явная связь на уровне базы данных. Ну есть и есть, какой от этого толк?

ON DELETE & ON UPDATE

Одно из замечательных свойств внешних ключей — возможность указать базе данных, что делать при удалении или изменении данных в связанной таблице.

Например, мы удаляем роль «Программист», и если бы таблицы не были связаны, то в таблице users остались бы пользователи, у которых в role_id лежит значение id только что удалённой строки в roles. Непорядок.

Чтобы это контролировать, стоит задать внешнему ключу поведение ON DELETE, которое может иметь одно из пяти значений:

  • RESTRICT — строго запретить удалять строку, на которую ссылается внешний ключ. Т. е. если мы захотим удалить роль «Программист», то эта стратегия не позволит удалять до тех пор, пока есть строки в users, ссылающиеся на удаляемую строку в roles. Часто используется, чтобы разработчики в своём коде делали все нужные действия по поддержанию консистентности данных.
  • NO ACTION — «мягко» запретить удалять строку, на которую ссылается внешний ключ. При удалении возникнет ошибка. Главная разница между RESTRICT и NO ACTION в том, что в транзакции RESTRICT сразу сделает ошибку, а NO ACTION дождётся конца транзакции, и ошибка может не возникнуть (если в процессе транзакции были удалены все ссылки на удаляемую строку). Устанавливается по умолчанию, если не задано иное.
  • CASCADE — удалить по цепочке все строки с внешними ключами, которые ссылались на удаляемую строку. При этой стратегии, если удалим роль «Программист», из таблицы пользователей удалятся все пользователи со ссылкой на эту роль.
  • SET NULL — говорит само за себя: при удалении данных, на которые ссылается внешний ключ, — поставить NULL (если колонка NULLABLE).
  • SET DEFAULT — также говорит само за себя: установить значение, прописанное по умолчанию при создании таблицы.

Для ON UPDATE действительны такие же значения.

Объявление внешних ключей при создании таблицы

Для того чтобы внешние ключи объявить сразу при создании таблицы, впишите после всех полей уже известный вам синтаксис создания внешнего ключа:

CREATE TABLE users (
	id SERIAL PRIMARY KEY,
	name VARCHAR(255) NOT NULL,
	role_id integer,
	CONSTRAINT roles_fk FOREIGN KEY (role_id) REFERENCES roles (id)
);
