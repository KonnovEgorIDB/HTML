Модификация данных

Прежде всего рассмотрим, как в базе делать стандартные операции CRUD — Create, Read, Update, Delete.

Запись (Create)

Для вставки новых строк в таблицы используется команда INSERT. Воспользуемся ею и добавим немного данных в базу:

INSERT INTO users (name) VALUES ('Vladimir'), ('Olga'), ('Viktor'), ('Elena');
INSERT INTO cookies (value, owner_id) VALUES 
('Vladimir cookie', 1), 
('Olga cookie', 2), 
('Viktor cookie', 3), 
('Elena cookie', 4);

В этих запросах не фигурирует колонка id, потому что она имеет атрибут auto increment и сама следит за своим состоянием. Если сейчас посмотреть в данные таблицы (в pgadmin это делается в контекстном меню таблицы, пункт «Просмотр/редактирование данных → Все строки»), увидим там строки с правильными id.

Чтение (Read)

Для чтения данных из базы используется команда SELECT. Выполните по очереди следующие команды и посмотрите на результат:

SELECT name FROM users;
SELECT * FROM cookies;
SELECT name FROM users WHERE id = 2;
SELECT * FROM cookies WHERE owner_id = 2;

Можно применять операторы фильтрации для получения более узкого объёма данных — фильтровать по одному или нескольким столбцам, объединять данные и многое другое. Чтобы лучше разобраться, советуем также глянуть эту статью.

В следующих уроках также рассмотрим объединение таблиц, когда, например, надо выбрать имя пользователя, если у нас есть значение его куки.

Обновление данных (Update)

Чтобы обновить часть данных (или строку целиком), используется команда UPDATE.

Например, пользователь меняет своё имя, или меняем значение куки пользователя:

UPDATE users SET name = 'Vlad' WHERE name = 'Vladimir';
UPDATE cookies SET value = 'new cookie' WHERE owner_id = 1;

Не забывайте использовать WHERE, чтобы изменить данные в нужных строках, иначе значение изменится во всех строках.

Удаление данных (Delete)

Удаление так и пишется — DELETE. Опять же, не забывайте про WHERE, иначе сотрёте все строки.

DELETE FROM users WHERE id = 2;

Если надо не просто удалить данные, но и получить их после выполнения, можно воспользоваться оператором RETURNING:

DELETE FROM users WHERE id = 3 RETURNING *;

Изменение структуры таблиц

Представьте ситуацию — вы выпустили в релиз первую версию продукта. Но завтра приходят задачи добавить новый функционал, который подразумевает добавление или изменение полей в таблице.

Для этого можно применить ALTER TABLE.

CREATE TABLE user_settings (
  id SERIAL PRIMARY KEY,
	text VARCHAR(255),
	...
);

# Добавить колонку
ALTER TABLE user_settings ADD COLUMN some_field INTEGER;
# Удалить колонку
ALTER TABLE user_settings DROP COLUMN some_field;

# Изменить тип колонки
ALTER TABLE user_settings ALTER COLUMN text TYPE TEXT;
# Изменить свойства колонки
ALTER TABLE user_settings ALTER COLUMN text SET NOT NULL;

# Переименовать колонку
ALTER TABLE user_settings RENAME TO personal_settings;

Миграции

Отдельно стоит рассказать про миграции. Это инструмент изменения структуры базы данных, который поддерживает историю изменений, их применение и откат.

Представьте, что вы с командой работали с базой данных, которая лежит на стейдж-сервере (а-ля тестовый сервер), то есть локально базу на своих компьютерах не поднимали, а если надо было что-то изменить в структуре БД, то согласовывали со всеми разработчиками, соединялись с базой и делали ALTER TABLE.

Это не самый удачный подход, но до сих пор встречается. Основные проблемы при этом подходе:

  • Поддержание консистентности состояния базы на стейдже и в продакшне. Если всё удачно получилось на стейдже — надо это же проделать на продакшне. А если неудачно — не забыть откатить стейдж. Если забыли откатить стейдж — структура баз данных начала разниться, и эта разница будет только расти.
  • Страдает developer experience — если кто-то вчера вечером поменял что-то в базе, а вы с утра забыли сделать rebase master — вас ждёт неприятное напоминание об этом.
  • Опять же про DevExp — если нескольким коллегам надо менять структуру базы — надо договариваться, как это сделать консистентно, и согласовать релизы. Это в свою очередь может делать задачи созависимыми, что неприятно.
  • В конце концов, ходить руками в базу на продакшне — это очень плохо.

Если бы у каждого разработчика была своя база на компьютере и не использовались бы миграции — всё было бы ещё сложнее.

Чтобы избежать этих и других проблем, используются миграции. Они очень похожи на систему контроля версий, но только про базу данных. Миграции чаще всего представляют из себя связку «библиотека миграций» + «файлы миграций». Если что-то пошло не так, то миграции можно откатить. При этом файлы миграций — это обычные файлы с кодом на том языке, на котором ведётся разработка. Эти файлы попадают в репозиторий, а значит, вся команда знает, что происходит в базе, каждый разработчик может обновить структуру своей локальной БД безболезненно.

Чаще всего библиотека миграций встроена в библиотеку ORM (Object-Relational Mapping). Сейчас не будем рассматривать ORM, но если вы работали с TypeORM, Mongoose или Sequelize — то это они и вы с ними знакомы.

Транзакции

Про них можно говорить много и долго, но скажем основное. Транзакции — это всё или ничего.

Рассмотрим пример запроса:

BEGIN;

UPDATE users SET account = account - 10000
WHERE id = 3;
UPDATE users SET account = account + 10000
WHERE id = 4;

{ COMMIT | ROLLBACK };

Транзакция — это один запрос на сразу несколько изменений. Если где-то по пути в этой транзакции что-то отвалится, то откатится вся транзакция и все её изменения в итоге не будут применены в базе.
