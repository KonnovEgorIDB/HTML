Docker Compose

Ранее мы уже рассмотрели базовую работу с докером и описанием контейнера. Но как быть, если для приложения требуется не один контейнер, а много? Ведь могут понадобиться реляционная база данных, нереляционная, шина… Если под каждую сущность описывать свой контейнер, то как их вместе запускать? Скопировать в README.md все команды и копировать оттуда в терминал? Не выглядит как хорошая идея.

Решение есть — утилита docker-compose, которая идёт в комплекте с Docker. Её суть в следующем: простым и понятным yaml-языком описать, какие контейнеры надо запускать, в каком порядке, какие порты и папки пробросить, а дальше она сделает всё сама. Да, docker-compose позволяет одной командой запустить сколько угодно контейнеров так, как вы опишете.

Конфигурация

Настройки для docker-compose описываются в файле docker-compose.yaml, он состоит из следующих позиций:

verison: "3"  # версия синтаксиса, оставляем 3, пока не выйдет новый docker-compose

services:  # самая главная секция, тут опишем, какие контейнеры запускать
	service1:
		...  # тут описываем настройки контейнера
	service2:
		...
# и т. д.

Для начала давайте запустим наш контейнер не через Docker, а через docker-compose. Для этого нужно:

  • собирать контейнер из описанного Dockerfile;
  • пробросить из контейнера 3000 порт;
  • пробросить в контейнер папку ./shared.

Опишем это в синтаксисе docker-compose:

# docker-compose.yaml
version: "3"

services:
  server-app:
		# Этим ключом мы скажем docker-compose, чтобы он собирал Dockerfile, который 
		# находится в папке рядом с docker-compose.yaml
    build:
      context: .
		# Проброс порта так же, как в командной строке — на какой порт хоста какой порт контейнера
    ports:
      - "4000:3000"
		# Проброс файлов, откуда с хоста, куда в контейнер
		volumes:
      - ./shared:/var/www/shared

Есть одно отличие от того, как производился запуск Docker в первом модуле — проброс папок. В docker-compose можно использовать относительные пути, и это очень удобно для командной работы: у каждого разработчика проект хранится где угодно на его машине, но docker-compose знает, что папку shared надо прокидывать именно из директории с проектом.

Запуск контейнеров с помощью docker-compose

Пришло время запустить контейнер. Для этого запустите команду docker-compose up server-app. Вообще её синтаксис такой: docker-compose up %service-name%, где %service-name% — название сервиса в секции services.

Если всё прошло успешно — в консоли вы увидите что-то похожее:

Starting docker_lesson_server-app_1 ... done
Attaching to docker_lesson_server-app_1
server-app_1  | Server running at http://0.0.0.0:3000/

Убедитесь, что всё работает, — откройте в браузере localhost:4000, поизменяйте файл в shared, посмотрите на результат. Остановите процесс с помощью Ctrl+C.

Как и у Docker, у docker-compose для запуска есть ключ -d, чтобы запустить процесс в фоне. Запуск контейнеров в фоне — самый используемый вариант, хотя если нужно посмотреть stdout — можно запускать без ключа -d.

Мониторинг и остановка контейнеров

Просмотр запущенных контейнеров с использованием docker-compose ничем не отличается от Docker: docker-compose ps. Однако, чтобы увидеть имена запущенных сервисов, надо использовать дополнительный ключ: docker-compose ps --services.

Остановка контейнеров немного отличается, хотя команда похожа на ту, что используется в Docker — stop. Но в качестве аргумента передаётся имя сервиса, а не идентификатор запущенного контейнера: docker-compose server-app.

Так же можно остановить вообще все запущенные контейнеры в текущем контексте docker-compose, просто написав stop без аргументов: docker-compose stop.

Надо объяснить, что имеется в виду под контекстом. docker-compose не может работать без файла docker-compose.yaml. Другими словами — docker-compose может работать только в той папке, где есть его конфигурационный файл. Такая папка здесь подразумевается под контекстом. У вас может быть много проектов, в каждом из которых будет docker-compose.yaml. Можно не бояться, что выполнение docker-compose stop остановит контейнеры из другого проекта.

Связывание контейнеров

В docker-compose.yaml можно описать несколько сервисов. Это удобно, когда достаточно в одном файле описать все настройки окружения, и каждый разработчик сможет поднять это на своей машине одной командой.

Для примера добавим в наш файл сервис с MongoDB.

В первую очередь надо найти образ с MongoDB на hub.docker.com и почитать его документацию. Вот официальный образ mongo. Нас в нём интересует несколько вещей:

  • как задать логин и пароль для доступа к монге;
  • где монга хранит свои файлы, чтобы пробросить туда папку.

Найдите эти моменты в документации самостоятельно и возвращайтесь.

Настраиваем конфигурацию

Добавим в раздел services новый сервис, назовём его mongo (вы можете назвать, как вам удобно) и допишем зависимость от него к нашему server-app.

Также настроим сеть внутри docker-compose, которая свяжет сервисы.

# docker-compose.yaml
version: "3"

services:
	# MongoDB ставим впереди server-app, так как тот server-app от этого сервиса
	mongo:
		# Здесь именно image, потому что мы его сами не пишем, он будет взят с докерхаба
		image: mongo
		environment:
			MONGO_INITDB_ROOT_USERNAME: user
			MONGO_INITDB_ROOT_PASSWORD: password
		volumes:
		  - ./mongo:/data/db
		ports:
		  - "27017:27017"
		# Появился новый параметр — networks, о нём ниже
		networks:
			# Назвать сеть можно как угодно
			- awesome

  server-app:
		# Этим ключом мы скажем docker-compose, чтобы он собирал докерфайл, который 
		# находится в папке рядом с docker-compose.yaml
    build:
      context: .
		# Проброс порта так же, как в командной строке — на какой порт хоста какой порт контейнера
    ports:
      - "4000:3000"
		# Проброс файлов, откуда с хоста, куда в контейнер
		volumes:
      - ./shared:/var/www/shared
		# Зависимость от сервиса mongo
		depends_on:
			- mongo
		# Важно добавить сеть всем сервисам, которые должны взаимодействовать между собой
		networks:
			- awesome

# Настройки созданной сети между сервисами
networks:
	awesome:
		driver: bridge

Запустите сервис docker-compose up -d server-app и посмотрите вывод docker-compose ps — там будут уже два запущенных сервиса. Если сейчас остановить только server-app, контейнер с MongoDB продолжит работать. Подключитесь к нему с помощью вашей утилиты для работы с Mongo и проверьте, что всё в порядке. Также обратите внимание на содержимое папки mongo: там появились служебные файлы базы данных, и теперь ей не страшны перезапуски — все данные хранятся в хостовой системе.

Ставим node_modules и драйвер mongodb

Чтобы проверить связь с MongoDB из нашего приложения, нужно внести несколько правок.

Во-первых, нужно создать package.json и записать туда зависимость mongodb, чтобы можно было подключаться к базе.

Во-вторых, изменить Dockerfile, чтобы он корректно копировал приложение в контейнер и при сборке делал npm install.

В третьих, подредактировать скрипт и научить его работать с базой данных.

И наконец, нужно немного изменить файловую структуру. С этого и начнём.

Пока у нас был один скрипт — особых проблем его скопировать в контейнер при сборке не было. Но наши приложения всегда имеют множество файлов, и чтобы не превращать файловую структуру проекта в помойку — выделим файлы приложения в папку app (но прежде создадим её). Файловая структура получится вот такой:

% tree .
.
├── Dockerfile
├── app
│   └── simpleServer.js
├── docker-compose.yaml
├── mongo
│   └── .gitkeep
└── shared
│   └── .gitkeep
│   └── text.json

Добавляем в папку app файл package.json и пишем туда зависимость:

{
  "name": "docker-lesson",
  "version": "1.0.0",
  "dependencies": {
    "mongodb": "3.6.5"
  }
}

Изменяем Dockerfile, чтобы файлы приложения корректно копировались в контейнер:

FROM ubuntu:18.04
RUN apt update && apt install -y nodejs && apt install -y npm
WORKDIR /var/www
# Слеши в конце означают, что надо все файлы из папки app скопировать в папку /var/www/
COPY app/ /var/www/
# При сборке контейнера в нём нужно исполнить npm install, и в папке /var/www
# будет лежать папка node_modules
RUN npm install
EXPOSE 3000
CMD node simpleServer.js

Теперь пора написать в скрипт работу с базой данных. Напишем простейшее подключение:

const http = require('http');
const fs = require('fs');
// Подключаем библиотеку драйвера
const MongoClient = require('mongodb').MongoClient;

const hostname = '0.0.0.0';
const port = 3000;

const server = http.createServer((req, res) => {
  const sharedValue = fs.readFileSync('./shared/text.json');
  res.statusCode = 200;
  res.setHeader('Content-Type', 'text/plain');
  res.end('Hello World' + sharedValue);
});

// mongo connection URL
// Обратите внимание на хост - mongo
const url = 'mongodb://mongo:27017';

const dbName = 'docker-lesson';
const client = new MongoClient(url);

client.connect(function(err) {
  if (err) {
    console.error('Cant connect to MongoDB');
    throw err;
  }
  console.log('Connected successfully to server');

  const db = client.db(dbName);

  server.listen(port, hostname, () => {
    console.log(`Server running at http://${hostname}:${port}/`);
    console.log('Database: ', db);
  });
});

По коду какие-то объяснения излишни. Всё стандартно, за исключением URL для соединения с базой данных. Почему адрес содержит mongo:27017?

При написании docker-compose мы указали обоим сервисам сеть. Теперь, когда docker-compose запускает контейнеры, — он создаёт между ними локальную сеть, знает, какие IP-адреса имеют контейнеры, и в каждый контейнер прописывает в файл hosts строки-алиасы с именами контейнеров и их адресами (на самом деле не совсем так, но смысл именно в этом). Поэтому по хосту mongo резолвится нужный IP-адрес.

Пересборка контейнера с docker-compose

После всех этих действий можно попробовать запустить контейнер. И получить то, на чём остановились в первый раз, — запустится сервер. Но почему? Мы же изменили Dockerfile, сильно изменили, как так? Дело в том, что надо явно сказать docker-compose пересобрать образ. Для этого выполните docker-compose build server-app. Если у вас сервис в docker-compose.yaml называется по-другому, используйте его имя.

Теперь при запуске сервиса «на холодную» (то есть после остановки всех сервисов) вы получите в консоль сообщение об ошибке из ноды:

MongoNetworkError: failed to connect to server [mongo:27017] on first connect

Если такого сообщения вы не получили — значит, запускаете сервис приложения с уже запущенным сервисом mongo. Остановите всё с помощью docker-compose stop, а затем docker-compose up server-app — ошибка должна случиться, потому что MongoDB стартует не мгновенно. Да, контейнер с ней поднялся, и docker-compose командует подъём контейнеру с нашим приложением. А в это время движок MongoDB ещё запускается. От этого и происходит ошибка.

Если спустя некоторое время попробовать запустить контейнер с приложением — всё будет хорошо, сервер поднимется, соединение с базой установится. Но для боевых условий, конечно, не подходит такой ручной менеджмент запуска — дожидаться, пока всё заведётся.

Настраиваем ожидание старта MongoDB

Воспользуемся инструментом wait-for. Создайте папку utils, положите в неё файл wait-for.sh и скопируйте в него соответствующий код.

Теперь надо опять поредактировать Dockerfile.

Во-первых, нужно поставить netcat — утилиту, которая нужна для работы wait-for.

Во-вторых, необходимо скопировать wait-for.sh в контейнер и дать ему права на исполнение.

В третьих, разнообразия ради, перенесём CMD из Dockerfile в docker-compose.

Дописываем соответствующие команды в Dockerfile (и CMD удаляем):

FROM ubuntu:18.04
# В эту строку добавилась установка netcat
RUN apt update && apt install -y nodejs && apt install -y npm && apt install -y netcat
WORKDIR /var/www
COPY app/ /var/www/
# Копируем wait-for
COPY utils/wait-for.sh wait-for.sh
# даём ему прав на запуск
RUN chmod +x wait-for.sh
RUN npm install
EXPOSE 3000
# CMD больше нет

Теперь сам контейнер ничего не запустит. Чтобы запустить наш сервер, надо в docker-compose.yaml дописать к сервису параметр command:

command: ./wait-for.sh mongo:27017 -- node simpleServer.js

Это укажет docker-compose, что после старта контейнера надо выполнить команду ./wait-for.sh с аргументами mongo:27017 -- node simpleServer.js. mongo:27017 — это тот адрес, ответа которого надо дождаться, а через двойной минус та команда, которую надо будет запустить после ответа ожидаемого сервера.

Пересоберите контейнер, и всё должно запуститься корректно.

Заключение

Вы познакомились с основами docker-compose, которых достаточно для продуктивной работы. Перед тем как приступить к базам данных, надо разобраться с последним моментом — с переменными окружения, потому что хранить логин-пароль от базы в docker-compose.yaml и название сервиса mongo в коде приложения — это дичь далеко не лучшая практика. Такие вещи должны быть конфигурируемы снаружи.

И небольшой квиз напоследок.

1) Какое преимущество дает использование alpine-версий образа? Если такая имеется

  • Никакого преимущества, просто другие название

  • Дает возможность использовать свежие бета-версии продукта, образ которого используем

  • Специальная версия Linux в основе контейнера, из которой вынесены все утилиты, которые не влияют на запуск и работоспособность продукта

2) Что означает запись 5002:5000 в docker-compose.yml?

  • Проброс 5002 порта контейнера на 5000 сервера, где запущен docker-compose

  • Проброс 5000 порта контейнера на 5002 сервера, где запущен docker-compose

  • Открытие всех портов для доступа в контейнер с 5002 по 5000

3) Параметр depends_on в docker-compose.yml содержит имена контейнеров, которые…

  • Нужно запустись до запуска контейнера

  • Нужно запустись после запуска контейнера

  • Не могут быть запущены во время запуска контейнера
