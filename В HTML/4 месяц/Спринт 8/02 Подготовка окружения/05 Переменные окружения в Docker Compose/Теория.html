Переменные окружения в Docker Compose

Введение

Нельзя хранить секреты (такие как пароли, логины, ключи) в репозитории. Так к ним будут иметь доступ если не все, то многие. Для хранения таких вещей созданы специальные хранилища, которые контролируются системными администраторами, и всё тайное останется тайным. Также нелогично завязываться в коде приложений на служебные переменные, которые задаёт окружение. В нашем случае такой переменной будет хост сервиса MongoDB. А если по решению разработчиков сервис в docker-compose.yaml будет переименован? Разве это повод лезть в исходный код и заменять там название переменной? Нет.

Также встаёт вопрос удобства разработчиков. Что если мы хотим протестировать наше приложение в продакшн-окружении (делайте это аккуратно) или в окружении стейджинга? Для каждого окружения нужны разные адреса, логины и пароли.

Для решения таких ситуаций лучше всего подходят переменные окружения — они задаются извне приложения, их может настроить системный администратор, они не попадают в систему контроля версий — то, что доктор прописал!

В этом уроке настроим docker-compose на работу с переменными окружения. Как это сделать при работе с Docker, попробуйте найти сами.

Подготовка приложения

Прежде чем настраивать docker-compose, настроим приложение. Для этого надо подключить в package.json библиотеку dotenv и использовать её в скрипте.

{
  "name": "docker-lesson",
  "version": "1.0.0",
  "dependencies": {
    "mongodb": "3.6.5",
    "dotenv": "8.2.0"
  }
}

const http = require('http');
const fs = require('fs');
// Подключаем библиотеку драйвера
const MongoClient = require('mongodb').MongoClient;

require('dotenv').config()

console.log(process.env.MONGO_HOST);
console.log(process.env.MONGO_PASSWORD);

// ...

Используем две переменные окружения — MONGO_HOST и MONGO_PASSWORD. MONGO_HOST будем задавать в файле docker-compose.yaml, а MONGO_PASSWORD в файле окружения.

Пересоберите контейнер, запустите и убедитесь, что консоль два раза выводит undefined.

Подготовка конфигурации

Пробрасывать переменные окружения в docker-compose можно двумя способами, и именно для этого мы берём две переменные. Логично, что если за имя сервиса, в котором запущена MongoDB, будет отвечать файл docker-compose.yaml, ведь именно он является источником истины — в нём прописано имя сервиса. А за MONGO_PASSWORD пусть отвечает файл, который будет дан нашей системе извне, например системным администратором.

Начнём с MONGO_HOST. Для того чтобы в файле docker-compose задать переменные окружения, служит директива environment:

server-app:
  # ...
  environment:
    - MONGO_HOST=mongo

В ней описываются переменные и их значения. В данном случае передаём значение mongo (соответственно с именем сервиса с базой данных) в переменную MONGO_HOST.

Чтобы передать неизвестные нам во время разработки переменные (которые делает системный администратор например), надо договориться с ответственным человеком, чтобы он сделал так, что при запуске контейнеров рядом с docker-compose будет лежать файл с переменными окружения. Для примера назовём его dev.env:

MONGO_PASSWORD=password

Теперь передадим его в docker-compose с помощью директивы env_file:

server-app:
  # ...
  environment:
    - MONGO_HOST=mongo
	env_file:
		./dev.env

Обратите внимание, что этот файл лежит на уровне с docker-compose.yaml, не в папке приложения (app), и не попадает при сборке в контейнер. Docker-compose возьмёт этот файл и сделает всё, что нужно, чтобы переменные из файла оказались в контейнере.

На этом приготовления к переменным окружения закончены — запустите сервис приложения и убедитесь, что в консоль попадают правильные значения.

local/stage/prod environments

Для того чтобы удобно переключаться между средами разработки, вам нужно научиться переопределять ваши переменные окружения. Для этого используют довольно простой подход:

  • В команде договариваются, что файл .env будет хранить переменные окружения (чтобы не изменять его имя в файле docker-compose.yaml).
  • Настраивают docker-compose под работу с этим файлом.
  • Добавляют файл .env в .gitignore (чтобы секреты не попали в Git, и чтобы каждый разработчик мог менять этот файл, не опасаясь за конфликты при слиянии).
  • В README.md прописывают инструкцию по настройке этого файла (каким переменным, какие значения желательно задать для удобной разработки).
  • В README.md пишут, где раздобыть значения переменных для других стендов (стейджинг, продакшн и так далее), и о том, что эти значения надо прописать в файл .env, чтобы приложение запустилось в нужной среде.
  • Радуются жизни, когда все переменные не лежат в Git, а все разработчики знают, как ими пользоваться.

Заключение

Теперь у вас достаточно знаний о контейнеризации, о том, как настраивать и запускать ваши контейнеры и пробрасывать в них переменные (это нужно часто). Конечно, это не исчерпывающая информация, но достаточная для того, чтобы теперь самостоятельно гуглить и понимать, что вам надо и как это сделать.
