Темизация

Многие сервисы предоставляют возможность поменять тему оформления, например со светлой на тёмную. Некоторые идут дальше и добавляют разные цветовые схемы на любой вкус. Иногда можно встретить темы, созданные специально под какие-то события, праздники или время года. Пространство для фантазии безгранично. Например, в мессенджере Slack предусмотрены светлая и тёмная основы и восемнадцать палитр для них. Плюс возможность создать свою палитру, что делает количество вариантов почти бесконечным.

В проекте вам предстоит добавить минимум одну дополнительную тему. Если есть желание сделать больше — границ нет! Творите!

В этом уроке покажем, как добавить темизацию на сервере и на клиенте.

Серверная часть

В прошлых темах уже рассказывали, как настроить базу данных, поэтому пропустим эту часть и перейдём сразу к «экшену».

Сперва настроим нужные таблицы. При работе с темизацией нужна как минимум одна — таблица с темой пользователя. Почему мы просто не добавим дополнительное поле в таблицу самого пользователя? У такого подхода есть несколько недостатков:

  1. При большом количестве пользователей и данных, таблица будет крайне большая и тяжёлая. Её будет сложно разносить со всеми данными пользователя на разные сервера. Гораздо проще разносить разные таблицы, в которых лежат нормализованные данные.
  2. Архитектурно неправильно хранить «все яйца в одной корзине». У пользователя есть основная персональная информация. Всё дополнительное должно регулироваться отдельными сущностями и таблицами. Так проще манипулировать данными.

Почему «как минимум»? Потому что темы могут быть динамическими в ходе жизненного цикла сервиса. Например, не хочется в список выбора текущей темы каждый раз добавлять (или удалять) строчку, чтобы пользователь видел, что на клиент приходят новые темы. Хочется поправить в базе данных активные темы и получить их через «ручку» на клиенте.

Для этого нужно завести ещё одну таблицу для хранения всех тем сервиса, чтобы ими можно было регулировать темы, например, через «админку» (какие-нибудь CMS, даже самописные).

Итого остановимся на двух таблицах:

  1. Таблица с темой, которая сейчас выбрана у пользователя на устройстве.
  2. Таблица со всеми существующими темами в проекте.

Создадим таблицу, которая будет использоваться для хранения текущей темы пользователя:

@Table({
  timestamps: false,
  paranoid: true,
  tableName: 'user_theme'
})
class UserTheme extends Model<UserTheme> {
  @AutoIncrement
  @PrimaryKey
  @Column(DataType.INTEGER)
  id: number;

  @AllowNull(false)
  @Column(DataType.STRING)
  theme: string;

  @Column(DataType.STRING)
  device: string;

	@ForeignKey(() => User)
  @AllowNull(false)
  @Column({
    type: DataType.INTEGER,
    field: 'owner_id'
  })
  ownerId: string;
}

В результате мы создали таблицу с четырьмя полями:

  • id — primary key строки;
  • theme — значение темы пользователя в сервисе;
  • device — опциональное поле на случай, если хотите запоминать с какого устройства у пользователя какая тема;
  • ownerId — foreign key на пользователя, у которого сохраняем тему.

Заметьте, мы не создаём поле theme как enum, потому что там могут быть произвольные строки (значения тем). Динамически изменять enum нельзя без обновления схемы данных.

Создадим таблицу всех тем:

@Table({
  timestamps: false,
  paranoid: true,
  tableName: 'site_theme'
})
class SiteTheme extends Model<SiteTheme> {
  @AutoIncrement
  @PrimaryKey
  @Column(DataType.INTEGER)
  id: number;

  @AllowNull(false)
	@Unique
  @Column(DataType.STRING)
  theme: string;

  @AllowNull(false)
  @Column(DataType.STRING)
  description: string;
}

Мы добавили ещё одну таблицу для хранения всех тем в базе. В таблицу можно добавить даже JSON(B) для хранения цветовой гаммы (переменных) и возвращать его сразу клиенту.

Теперь, когда у нас есть таблица тем, можем вернуться к таблице, в которой хранятся темы пользователя. Если вы сделали эти две сущности, то нужно будет добавить волшебное ForeignKey и поменять тип у поля theme таблицы user_theme.

@ForeignKey(() => SiteTheme)
@AllowNull(false)
@Column(DataType.INTEGER)
themeId: string;

Теперь это поле существует как надо.

Добавим индексы на некоторые поля. Например, добавим индекс на поле theme таблицы site_theme, поскольку будем часто делать поиск по тексту самой темы:

@Table({...})
	class SiteTheme extends Model<SiteTheme> {
	...
	
	@Index
	@AllowNull(false)
	@Unique
	@Column(DataType.STRING)
	theme: string;
	
	...
}

Декоратор также обладает возможностью задать параметры, которые можно почитать в документации. Все они соотносятся с параметрами индексов самой базы PostgreSQL.

Помните, не переусердствуйте с декораторами, вы можете сделать сервис намного медленнее.

Теперь, когда у нас есть таблицы, можем написать несколько «ручек» по работе с темами.

Если вы пишете свою CMS, можно сделать отдельную авторизацию и отдельные «ручки» по работе с темами. Вы можете также управлять данными напрямую через psql, DataGrip или любой другой подобный инструмент.

Начнём с роутера:

const server: Express = express();

server
	.disable('x-powered-by')
	.enable('trust proxy')
	.set('query parser', queryParser)
	.use(cookieParser())
	.use(logger)
	.use(router)
	.use(notFound);

Перед запуском сервера нужно будет явно запустить Sequelize. Например, так:

(async function() {
	await sequelize.sync({force: true});
	server.listen(...);
})();

В роутере будет храниться весь набор ручек различных сущностей:

const router: Router = Router();

appRoutes(router);
staticRoutes(router);
userThemeRoutes(router);
themesRoutes(router);
healthRoutes(router);
dadataRoutes(router);

export default router;

Далее создадим контроллер по работе с темами, после чего покажем, как их зарегистрировали в отдельный роутер. Создадим абстрактный базовый класс по работе с сервисом:

abstract class BaseRESTService {
  abstract request?: (...args: any[]) => Promise<any>;
  abstract create?: (...args: any[]) => Promise<any>;
  abstract update?: (...args: any[]) => Promise<any>;
  abstract delete?: (...args: any[]) => Promise<any>;
  abstract find?: (...args: any[]) => Promise<any>;
}

Создадим сервис для работы с темами:

interface FindRequest {
	id?: number; // ID темы в таблице
	title?: string; // Поиск по частичному совпадению в таблице
}

interface CreateRequest {
  title: string;
  description: string;
}

class ThemeService implements BaseRESTService {
  public find = ({id, title}: FindRequest) => {
    if (id) {
	    return siteThemeRepository.findByPk(id);
    }

    return siteThemeRepository.findOne({
      where: {
        theme: `%${title}%`, // Защита от SQL Injection присутствует
      },
  });
  };

  public create = (data: CreateRequest) => {
    return siteThemeRepository.create(data);
  }
}

Сервис состоит из двух методов: найти и создать. Если вам нужны дополнительные методы по работе с сущностью (обновление данных, удаление) — можете добавить. Сервис отвечает за работу с самой сущностью.

Не стоит делать из метода сервиса универсальный метод, который умеет всё. Старайтесь выделять и разделять логику.

Теперь создадим контроллер для обработки запроса. Например, мы хотим по роуту GET /my-api/v1/theme/ сделать получение информации по теме. И по методу POST /my-api/v1/theme создавать тему. Контроллеры обрабатывают такие роуты:

class ThemeAPI {
	@validation({/* rules */}) // Можно использовать декораторы, можно передавать в middlewares
  public static create = async (request: ExpressRequestModeledType, response: ExpressRespinseModeledType) => {
		const {body} = request;
		/* Делаем что-то с данными */
		await themeService.create(body); // Можно обернуть в try..catch
  }
}

Теперь осталось зарегистрировать роут:

export const themesRoutes = (router: Router) => {
  const themesRouter: Router = Router();

  themesRouter
	  .post('/', [logger], ThemeAPI.create)
	  .get('/', [logger], ThemeAPI.find);

  router.use('/theme', themesRouter);
};

В мидлвари можно помимо logger передавать также валидаторы. Если вам удобнее декораторы, можно написать свои и использовать их целиком для контроллера без описания отдельного файла с «подроутером».

Вы можете задаться вопросом, зачем создавать почти одинаковые классы Service и Controller для одной сущности? Это делается для абстракции логики работы над сущностью и логики обработки ручки. Совсем не всегда эти вещи совпадают.

Например, у вас кейс — не просто создать данные из body, а перед этим:

  • применить к ним валидацию;
  • сходить в другую «ручку» и получить какие-то данные;
  • взять данные из другого сервиса;
  • соединить в новый объект;
  • наконец создать вашу сущность.

В коде это выглядело бы примерно так:

class ThemeAPI {
	@validation({/* rules */}) // Можно использовать декораторы, можно передавать в middlewares
  public static create = async (request: ExpressRequestModeledType, response: ExpressRespinseModeledType) => {
		const {body} = request;

		const data1 = await someService.find(body.someId);
		const data2 = await someOtherService.find(body.otherId); // Или что-то ещё
		const data3 = prepareBody(body, data1, data2);

		/* Делаем что-то с данными */
		themeService.create(data3);
  }
}

В этом случае не нужно тащить в контроллер инстанс базы данных. Должна быть изолированная абстракция для работы с той или иной сущностью проекта.

Клиентская часть

Описывать часть по работе с «ручками» из «соседнего» API и хранением данных не будем. Здесь всё ровно то же самое. Единственное, у вас запросы в это новое API будут отправляться по немного другим роутам.

Расскажем, как реализовать переключение тем.

Контекст

В ReactJS это можно сделать через контекст. При создании главного компонента, который будет добавлен в DOM, можно добавить также провайдера (как и с Redux’ом или Router’ом).

const ThemeContext = React.createContext('light'); // По умолчанию будет тема `light`

Далее используем этот контекст при работе с компонентами, которые зависят от тем.

hydrate(
	<ThemeContext.Provider value="light">
    <Provider store={store}>
      <ConnectedRouter history={history}>
        <DesktopBundle data={data}/>
      </ConnectedRouter>
    </Provider>
	</ThemeContext.Provider>,
  document.getElementById('root'),
);

Такой способ позволяет прокидывать контекст в различные компоненты. После чего вы можете динамически менять необходимые классы стилей, цвета в CSS-in-JS.

Redux
