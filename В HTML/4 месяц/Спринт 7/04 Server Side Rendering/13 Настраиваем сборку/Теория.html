Настраиваем сборку

Начнём с настройки сборки проекта. С точки зрения архитектуры нам нужно:

  • TypeScript;
  • CSS, SCSS (можно заменить на любой другой препроцессор, если он вам нужен) или PostCSS (например, автопрефиксер);
  • работа с файлами, картинками, иной статикой.

Все конфигурации для Webpack будем реализовывать на TypeScript (ну а как же иначе).

Перейдём к архитектуре сборки. Процесс сборки будет состоять из нескольких этапов:

  1. Скомпилировать JS-бандл с вендорами проекта (react, react-dom).
  2. Скомпилировать конфигурационные файлы для проекта (конфиги хранят пути к статике и другую информацию, которой можно управлять через конфиги). Об этом подробнее напишем ниже.
  3. Скомпилировать сервер (тот, что Express и раздаёт проект).
  4. Скомпилировать клиент.

И ещё пятое действие (если мы в dev) — запустить watch-процесс, который будет по изменению в коде обновлять вашу страницу.

Собираем вендор

Составим конфиг, в котором опишем, какие вендоры нужно скомпилировать и куда их вывести. Пример файла:

// webpack/config/vendors.config.ts

import {join} from 'path';
import webpack from 'webpack';

import {VENDORS} from '../assets/config';
import {ROOT_DIR_FROM_WEBPACK} from '../assets/dir';
import {ENVS} from '../assets/env';

const DIST_DIR = join(ROOT_DIR_FROM_WEBPACK, 'dist');

const config: webpack.Configuration = {
  target: 'web',
  devtool: 'source-map',
  entry: {
    vendors: VENDORS, // [ 'react', 'react-dom', ... ]
  },
  output: {
    library: '[name]_[hash]',
    filename: '[name]_[hash].js',
    path: join(DIST_DIR, 'client', '_'),
  },
  plugins: [
    new webpack.DllPlugin({
      name: '[name]_[hash]',
      path: join(DIST_DIR, 'webpack', 'vendors-manifest.json'),
    }),
  ],
};

export default config;

Полный файл вы можете посмотреть в нашем репозитории. Разберёмся с текущим сниппетом.

В entry задаём список необходимых вам библиотек в отдельном бандле. Через DLL-плагин собираем список необходимых зависимостей. На выходе получится JS-бандл и vendors-manifest.json, который будет нужен при сборке клиентской части.

Сгенерированный JSON-файл будет нужен в следующих сборках, потому добавим его генерацию при запуске установки зависимостей, например, сделав отдельный скрипт:

"init": "npm install && npm run build:dev:vendors". Можно воспользоваться хуком postinstall и навесить нужные команды после установки зависимостей.

Собираем сервер

Теперь нам нужно скомпилировать сервер. Компиляцию произведём утилитой tsc, указав нужный путь к папке: tsc --project server. После компиляции можно запускать процесс сборки сервера.

Серверная сборка отличается от клиентской.

Во-первых, для обработки файлов используются конфигурации, отличные от клиентских. Это сделано, поскольку на сервере, например, не получится корректно обработать стили. Однако их всё равно можно скомпилировать в CSS-бандлы.

Во-вторых, на сервере не существует никаких localStorage и window. Поэтому, если вы используете что-то из вышеназванного, вам нужно будет замокать данные сущности. Замокать можно любую необходимую логику. Например, вот так:

// webpack/mock/window.mock.ts

let win;

if (typeof window !== 'undefined' && typeof window.getComputedStyle === 'function') {
  win = window;
} else {
  win = {
    getComputedStyle() {
      return {
        getPropertyValue() {},
      };
	  },
    addEventListener() {},
  };
}

export default win;

// webpack/mock/localStorage.mock.ts

let localStorage;

if (typeof window !== 'undefined') {
  localStorage = window.localStorage;
} else {
  localStorage = {
    setItem() {},
    getItem() {},
  };
}

export default localStorage;

Подключить моки можно через ProvidePlugin. В нашей сборке это сделано так:

new webpack.ProvidePlugin({
  window: resolve(join(__dirname, '../mock/window.mock')),
  localStorage: resolve(join(__dirname, '../mock/localStorage.mock')),
  document: 'global/document',
}),

Подробнее пример можно рассмотреть на GitHub.

Кроме моков, в коде можно проверять, кто собирает данную часть: сервер или клиент. Это происходит через проверку наличия window в окружении:

const isServer = !(
  typeof window !== 'undefined' &&
  window.document
);

export default isServer; // можно импортировать и использовать везде

Такой приём может пригодиться при создании History объекта:

import isServer from 'path/to/checkServer';

const history = !isServer
	? createBrowserHistory()
	: createMemoryHistory({initialEntries: router?.initialEntries || ['/']});

Кроме того, можно рендерить компонент в зависимости от окружения. Например, если на сервере библиотека не сможет скомпилироваться, можно оборачивать компонент в подобный блок:

import isServer from 'path/to/checkServer';

export function renderOnClientSideOnly(
  Component: React.ComponentType,
  props: any,
) {
  if (isServer) {
	  return (
      <React.Fragment/>
	  );
  }

  return <Component {...props}/>;
}

Вы можете спросить: «Какие это библиотеки нельзя скомпилировать на сервере?» Например, популярную и крайне мощную библиотеку по работе с графиками Highcharts. Они, к сожалению, не умеют рендериться на сервере, но их функционал зачастую незаменим.

Сборка клиента

Клиентская сборка делается в двух местах:

  • в момент разработки для watch-режима;
  • сборка для окружения.

Сама сборка для всех идентична:

function getConfig(lang: string, index: number): webpack.Configuration {
  return flow([
    initClientConfig({lang, index}),
    loadScripts({isSSR: false}),
    loadStyles({isSSR: false}),
    loadAssets({isCopyStatic: false}),
  ])({});
}

export default cfg.langs.map(getConfig);

Весь процесс сборки также разбит на шаги:

  • описание точки входа, выхода и общих плагинов;
  • обработка скриптов;
  • обработка стилей;
  • обработка картинок, файлов.

В общих конфигурационных файлах мы храним ключ langs, который позволит собирать разные JS-бандлы в зависимости от языка (cfg.langs.map(getConfig)). На выходе будет, например, bundle.ru.[hash].js.

Для всех языков мы можем собирать отдельные бандлы, просто указав количество языков.

Расписывать каждый лоадер не будем, потому что вы можете добавлять нужные вам конфигурации, но покажем, как использовать два различных описания одного и того же процесса обработки стилей или скриптов. Для сервера будем использовать null-loader, чтобы не обрабатывать стили на сервере. Полностью лоадеры можно увидеть здесь.

// webpack/loaders/css.ts

export default {
  client: [
    {
      test: /\.css$/,
      exclude: /node_modules/,
      use: cssLoaders,
    },
    {
      test: /\.css$/,
      include: /node_modules/,
      use: [
        MiniCssExtractPlugin.loader,
        {loader: 'css-loader'},
        postcssLoader,
      ],
    },
      {
        test: /\.scss$/,
        use: [
          ...cssLoaders,
          sassLoader,
          {
            loader: 'sass-resources-loader',
            options: {
              resources: [
                'client/sass/_variables.scss',
								// ...
              ],
            },
          },
        ],
      },
  ],

  ssr: [
    {
      test: /\.scss$/,
      loader: 'null-loader',
    },
    {
      test: /\.css$/,
      loader: 'null-loader',
	  },
	],
};

На клиенте же можем использовать абсолютно любые необходимые нам модули. Из того, что может быть необычного, что можно не сразу найти в документации, — настройка CSS-модулей с возможностью загружать дополнительные стили из библиотек.

Вы можете столкнуться с проблемой, что в вашем проекте используются CSS-модули:

import styles from './Some.scss';

<div className={styles.wrapper}> // В браузере будет хешированиый стиль, например: _3a29IuLy
  ...
</div>

Но при этом, когда вы добавляете библиотеку, например, Ant Design или react-select, все стили будут также добавляться через import в CSS или TypeScript. Однако это добавляет проблем. Все классы в DOM-дереве будут хешированными. Поэтому мы добавили два лоадера для одного и того же вида файлов .css:

  • include: /node_modules/,;
  • exclude: /node_modules/,.

Для стилей, которые включают нод-модули, мы не используем CSS-модули, в отличие от тех стилей, которые созданы в самом проекте.

Подобное поведение можно реализовать не только через два лоадера, но и через один с обработкой входящих файлов через проверку путей. Какой способ вам удобнее и кажется более декларативным, тот и используйте.

Сборка для разработки

В момент разработки нас интересует обновление клиента при каждом изменении кода, например, как в webpack-dev-server с использованием hot module reload. Под капотом webpack-dev-server содержит обычный Express-сервер, в котором используются библиотеки:

  • webpack-dev-middleware,
  • webpack-hot-middleware.

Вся магия webpack-dev-server раскроется для вас ровно в следующем предложении, готовы? Это просто дополнительный middleware для Express с использованием двух библиотек выше!

Не верите? Смотрите!

import {RequestHandler} from 'express';
import webpack from 'webpack';
import devMiddleware from 'webpack-dev-middleware';
import hotMiddleware from 'webpack-hot-middleware';

import webpackConfigs from 'webpack/config/client.config';

import render from './render';

function getWebpackMiddlewares(config: webpack.Configuration, index: number): RequestHandler[] {
  const compiler = webpack({...config, mode: 'development'});

  return [
      devMiddleware(compiler, {
        logLevel: 'error',
        publicPath: config.output!.publicPath!,
      }),
      hotMiddleware(compiler, {path: `/__webpack_hmr_${index}`}),
  ];
}

Что мы здесь делаем:

  1. Импортируем конфиг для работы с клиентским кодом (выше про него говорили).
  2. Делаем компайлер из импортированной конфигурации.
  3. Настраиваем hot module reload.
  4. PROFIT!!!

Всё, что остаётся, — подключить данную мидлварю к роуту рендеринга самого продукта:

function render(req, res) {
	const jsx = (<div>Hello, My App!</div>);
	const reactHtml = renderToString(jsx);

	res.send(getHtml(reactHtml));
}

app.use('/', [mw1, mwi, ..., hmrMiddleware], render); // подключаем мидлвари

Напомним, что мидлвары исполняются поочерёдно перед каждым вызовом финального render.

Поздравляю, вы реализовали свой webpack-dev-server, который можете править так, как вам нужно, и тогда, когда вам нужно, без необходимости заглядывать в исходники библиотеки.

Сборка клиента для окружения

Здесь всё гораздо проще. Достаточно запустить скрипт webpack с указанием пути к конфигурационному файлу сборки клиента. Например, так:

webpack --mode=production --hide-modules --config webpack/config/client.config.ts

Итог

Теперь вы знаете, что под капотом webpack-dev-server, умеете настраивать сборку в SSR и как минимум понимаете, что здесь нет ракетостроения: всё делается через TypeScript, ExpressJS и Webpack. Достаточно немного заглянуть вглубь инструментов, и теперь вам не нужно завязывать на целую экосистему чужих команд (вроде NextJS).
