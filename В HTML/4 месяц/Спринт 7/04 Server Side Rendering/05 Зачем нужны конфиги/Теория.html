Зачем нужны конфиги?

А теперь обратим внимание на «тёмную лошадку» — конфигурационные файлы всего проекта. С виду тут ничего особенного и можно всё задать вручную. Но давайте рассмотрим такие случаи:

  1. Локальный путь к статике — это /dist/bundle.js, а на удалённом сервере в окружение production — это https://storage.cloud.yandex.ru/dist/bundle.hash.js.
  2. Нужен ли hot-reload в той или иной сборке.
  3. Какой уровень логов должен быть в приложении.
  4. Какие языки есть в приложении.
  5. Должен ли работать Service Worker в той или иной сборке.

Как такое можно решить:

  1. «Напихать» множество if-конструкций и сделать из Webpack или Express сервера нечитаемое и почти не контролируемое полотно кода с множеством ветвлений в зависимости от окружений.
  2. Сделать конфигурационные файлы, которые будут лежать в отдельной папке. Каждый файл будет начинаться с имени окружения, и именно конфиг с соответствующим окружением будет подгружаться в проект.

Приятнее читается второй способ. Попробуем внедрить его в проект. Предлагаем посмотреть на пример конфигураций в различных окружениях, которые мы добавили в наш проект.

Файл defaults.ts содержит общие значения для всех окружений. Все остальные файлы либо переопределяют то, что уже есть, либо описывают только то, что нужно для данного окружения. Например, в окружении production мы не хотим загружать скрипты, стили и остальную статику из папки рядом с проектом, а хотим загружать их из S3-хранилища:

import {AppConfig} from 'cfg';

const config: AppConfig = {
  static: {
    baseUrl: `//storage.yandexcloud.net/path/to/S3/${process.env.APP_VERSION}/client/`,
  },
};

module.exports = config;

Как это дело подключать?

Мы написали модуль, который считывает из process.env окружение, где находится продукт, и делает мёрж двух файлов:

  • defaults.ts;
  • <env>.ts.

В результате скрипт экспортирует уже смёрженные два файла. Таким образом, достаточно написать в серверном коде import cfg from 'lib/cfg', чтобы получить то или иное значение.

Как нужное окружение попадает в process.env? Например, через Webpack-сборку, в которой пробрасывается необходимое окружение. Или же через утилиту dotenv, которая позволяет через дополнительный файл явно указать окружение и положить его в переменные окружения.

Таким образом, вы можете задавать любые значения для всех окружений, манипулировать ими напрямую из конфигурационных файлов и не мучать файлы сборки или серверный код дополнительными проверками «а в каком же окружении я нахожусь?». Вместо этого можно напрямую указать cfg.myKey, в котором мы уверены, что будет необходимое значение для соответствующего окружения.
