Зачем мидлвари в SSR?

Мидлвари помогают упростить жизнь и не дублировать код. Например, вам перед бизнес-логикой Express-роута нужно проверить авторизацию пользователя и, если куки не валидные, вернуть код 401. Или вы написали роут, который принимает POST-запрос с JSON-телом.

Чтобы не проверять наличие ключей прямо в бизнес-логике роута, можно написать мидлварю, которая будет проверять наличие необходимых ключей. Таким образом, если клиент отправил на ваш сервер невалидный объект с неправильными ключами или типами значений, мидлваря сама вернёт 400-й ответ с причиной ошибки, и ничего до вашей бизнес-логики не дойдёт. Код станет чище.

Ниже рассмотрим примеры мидлварей, которые могут помочь упростить жизнь.

Логгер

Логирование никогда не бывает лишним. Особенно у веб-сервера. Поэтому будет полезным завести себе логгер и «повесить» его на необходимые «ручки». Например:

  • получение веб-приложения,
  • POST-запросы.
import {NextFunction, Request, Response} from 'express';

export default function () {
  return (req: Request, _res: Response, next: NextFunction) => {
    req.logger = () => {
			// Пишем свои логи в файл или используем готовые логгеры
    };
    next();
  };
}

Обработка 404 или 5** ответов

В случае, если ваш веб-сервер отвечает 404 или упал с ошибкой, верните пользователю что-то читаемое и красивое. Не нужно показывать плохие стороны проекта. Смягчайте удар. Такие мидлвари позволяют перехватить запросы и вернуть что-то более интересное.

import {NextFunction, Request, Response} from 'express';

export default function () {
  return (req: Request, _res: Response, next: NextFunction) => {
    req.render500 = () => {
			res.status(HTTPCode.InternalServerError); // 500
			// нужно отрендерить что-то для пользователей
    };
    next();
  };
}

Обработка ключей

Например, вы написали «ручку», которая по JSON-телу что-то изменяет в базе данных или делает запрос в другое API. Крайне полезно не захламлять свой код дополнительными проверками на наличие тех или иных ключей.

Можно воспользоваться, например, такой реализацией (или любой другой):

import {Request, Response, NextFunction} from 'express';
import isNil from 'lodash/isNil';

export interface Rule<K, V> {
  key: K;
  required?: boolean;
  validator?<T>(value: T | V): boolean;
}
export type Rules<K, V> = Rule<K, V>[];

export function validateBodyKeys<T extends object>(rules: Rules<keyof T, T[keyof T]> = []) {
	return ({body}: Request, response: Response, next: NextFunction) => {
	    try {
	      for (const {key, validator, required} of rules) {
	        const value = body[key];
	
	        if (required && isNil(value)) {
	          throw `${key} is empty, but required`;
	        }
	
	        if (validator && !validator(value)) {
	          throw `${key} is not valid`;
	        }
	      }
	
	      next();
	    } catch (reason) {
	      response.status(400).send({error: 'bad format', reason: reason.toString()});
	    }
	};
}

Определение данных пользователя

Здесь можно рассматривать даже не одну мидлварю, а целый комплект:

  • определение языка пользователя (langdetect);
  • определение платформы пользователя (desktop, mobile, tablet);
  • определение местоположения пользователя по пришедшему IP-адресу.

Вас ограничивают только ваши потребности.

Авторизация пользователя

Например, вам необходимо знать, авторизован ли пользователь. Вы можете сделать мидлварю, которая сама проверит куки пользователя (или другие способы авторизации, например JWT-токен) и отправит в бизнес-логику ответ, авторизован он или нет. В зависимости от этого вы уже можете решить, что отобразить пользователю и куда его перенаправить.

Информационная безопасность

Последний в списке, но не по значению. Вы можете добавлять проверку CSRF-токена для не GET-запросов или Content Security Policy. Server Side становится ещё одной точкой для атаки и злоумышленники могут без проблем «играться» с вашим веб-сервером на NodeJS и составлять новый вектор атаки. Например, попытаться подкложить XSS.
