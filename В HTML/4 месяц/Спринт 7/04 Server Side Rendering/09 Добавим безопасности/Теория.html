Добавим безопасности

CSP

Content Security Policy позволяют настроить взаимодействие с другими и даже своими веб-ресурсами.

Например, если не хотите, чтобы в ваше приложение встраивалась реклама через iframe с недоверенного источника, — просто укажите список разрешённых для данного сервиса источников, которые могут открываться в iframe. Или же кто-то хочет «подселить» к вам сторонний JavaScript, а у вас нет в разрешённых рекламы с сайта вроде «Азино Три Топора».

Таким образом, ваш продукт становится намного менее уязвим к векторам атаки, подразумевающим внедрение вредоносного кода, ссылок и других ресурсов. Но это не защищает от XSS и в целом не связано с этим. Лишь косвенно. Вредоносный HTML-код всё ещё могут вставить через renderToString.

Работа с CSP уже присутствует в библиотеке Helmet, которая позволяет управлять не только мета-тегами, но и инфраструктурой приложения в целом.

Однако мы воспользуемся отдельной библиотекой csp-header, с помощью которой напишем собственный модуль, который и будем использовать как мидлварю для добавления CSP.

Защита заключается не только в списках разрешённых источников, но и в добавлении дополнительного ключа в качестве атрибута в скрипты и стили. Таким образом, браузер и веб-сервер могут проверять, что инлайн-скрипты и стили являются тем, что сам веб-сервер корректно добавил.

По сути это как CSRF-токен. Сервер выставляет данный токен инлайн-скрипту и если исполняемый скрипт содержит некорректный токен, то скрипт выполнен не будет.

Здесь задействованны два механизма защиты:

  • списки разрешённых источников;
  • токен проверки скриптов и стилей.

Добавим оба.

Добавление nonce-токена

Рассмотрим модуль генерации csp-nonce-токена. Его основная задача — парсить домен, проверять CSP-политики, а также проверять nonce-токен.

В результате модуль выдаёт криптостойкий nonce-хеш, который и прикладывается в request Express через мидлварю.

Данный модуль просто добавляется в виде мидлвари перед рендером страницы:

import {ErrorRequestHandler, RequestHandler, Router} from 'express';

import {renderApp} from 'server/controllers';
import {
  cookieParser,
  cspHeader,
  helmet,
  csrfProtection,
} from 'server/middlewares';

const middlewares: Array<RequestHandler | ErrorRequestHandler> = [
  cookieParser,
  helmet,
  cspHeader,
  csrfProtection,
];

export function appRoutes(router: Router) {
  router.get('/', middlewares, renderApp);
}

Дальше в req попадает необходимое свойство nonce:

export default function renderApp(req: Request, res: Response) {
  const {nonce} = req;

  res.renderBundle('desktop', {
    nonce,
    // ...
  });
}

И последний штрих. Добавим этот nonce-токен в скрипты через функции рендера строки из JSX:

function getPageHtml(params: PageHtmlParams) {
  const {data} = params;
  // ...

  const html = renderToStaticMarkup(
    <html>
      <head>
				{ /* ... */ }
      </head>
      <body>
				{ /* ... */ }

        {vendorsMeta.hasJs && <script **nonce={data.nonce}** src={`${vendorsFilePath}.js`}/>}
        <script nonce**={data.nonce}** src={`${bundleFilePath}.ru.js`}/>
        <script
          nonce={data.nonce**}**
          dangerouslySetInnerHTML={{
            __html: `Client.default(${htmlescape(data)});`,
          }}
        />
      </body>
    </html>,
  );

  return `<!doctype html>${html}`;
}

Из представленного выше сниппета видно, что мы добавили токен nonce во все инлайн-скрипты. И теперь при получении документа в Network можно увидеть, что всё подставилось корректно:

Работаем со списками доступов

Политики задаются в виде заголовка Content-Security-Policy: default-src 'self';. Правила содержат хосты, макросы для предоставления доступа к ресурсу. Например, если в политике не добавлен сайт fonts.google.com, то ваши шрифты, которые подгружаете из Google, не подгрузятся. Браузер сам даже не запустит туда запрос, потому что нет политики, разрешающей делать туда запросы.

Но если добавить в политики style-src и font-src нужные хосты Goggle (например, 'fonts.googleapis.com', 'fonts.gstatic.com'), то всё подгрузится как надо.

Руками составлять строки не нужно, для этого есть модуль, который мы подключали выше. Просто воспользуемся им.

Чтобы описать правило, достаточно создать объект, ключами которого будет название политики, а значением — массив разрешённых хостов:

import {CSPDirectives} from 'csp-header';

const policies: CSPDirectives = {
  'style-src': ['fonts.googleapis.com'],
  'font-src': ['fonts.googleapis.com', 'fonts.gstatic.com'],
};

export default policies;

Если вы хотите разрешить все поддомены определённого уровня — можете использовать квантификаторы, как в регулярках: *.my.super.domain.com.

В нашем примере мы разбиваем политики на подгруппы:

  • Google-шрифты.
  • API-хосты. Причём хосты также разделяются по окружениям. Неправильно разрешать из продакшена делать запросы в тестинг и наоборот.
  • Доступ до статики с собственного сервера (да, можно запретить ходить даже «в себя»).

Все примеры наших политик можно посмотреть на GitHub. Мы их называем «пресетами».

Теперь научимся не просто описывать политики, но и подключать их к проекту, чтобы они работали.

Для это воспользуемся нашей любимой «тёмной лошадкой» — конфигами. Благодаря конфигам мы сможем задать различные правила для разных окружений и даже не переживать из-за if-конструкций.

По умолчанию всем окружениям зададим общие политики:

import {AppConfig} from 'cfg';
import {join} from 'path';

import defaultsCsp from './csp/defaults';

const config: AppConfig = {
  csp: {
    presets: defaultsCsp,
    policies: {},
    serviceName: 'ssr-app',
    useDefaultReportUri: true,
  },

	// ...
};

module.exports = config;

Для каждого окружения зададим дополнительные пресеты, которые относятся только к данному окружению. Посмотреть все конфиги можно на GitHub.

Осталось дело за малым — подключить. Сама мидлваря остаётся той же, что и была выше: cspHeader. Рассмотрим подробнее инициализацию данной мидлвари:

import cfg from 'lib/cfg';

// ...

const cspHeader: RequestHandler = expressCspHeader(cfg.csp);

Это говорит о том, что мидлваря полностью зависит от конфига, а значит все правила будут корректными для каждого окружения.

Теперь мы можем убрать 'self' правило из скриптов и посмотреть, что браузер не загрузит наши скрипты и выведет в консоль ошибку.

CSRF

С CSRF всё в разы проще. Мы можем использовать библиотеку csurf (не забудьте поставить типы из @types, без них TypeScript будет ругаться на наличие свойства в Request).

После установки достаточно проинициализировать мидлварю и начать использовать:

// server/middlewares/index.ts

import csrfMiddleware from 'csurf';

// ...

const csrfProtection: RequestHandler = csrfMiddleware({cookie: true});

// server/router/app.ts

import {
		// ...
    csrfProtection,
} from 'server/middlewares';

const middlewares: Array<RequestHandler | ErrorRequestHandler> = [
    // ...
    csrfProtection,
];

export function appRoutes(router: Router) {
    router.get('/', middlewares, renderApp);
}

Теперь через Request можно вытащить значение токена. Токен будет проверяться при не GET-запросах. Можно настраивать дополнительные правила обработки токена.
