Локальные хранилища

localStorage и sessionStorage

Бывают ситуации, когда фронтенд-приложение должно сохранить какие-то данные на длительный срок, но при этом сделать это без бэкенда. Представьте в модальном окне большую и сложную форму с десятками полей (да, десятки полей — это плохой UX, но для примера самое то). Пользователь сидит и долго заполняет данные, тянется мышью к следующему полю, промахивается и кликает вне модального окна — модалка закрывается, форма теряет свои значения. Или кошка пробежала по клавиатуре, нажала F5, и страница перезагрузилась. Представляете отчаяние и боль?

Для защиты от таких ситуаций было бы хорошо сохранять вводимые данные, чтобы можно было легко их восстановить. Отправлять на каждый ввод запрос на сервер — слишком дорогая операция. И здесь нам помогут браузерные хранилища данных.

В браузере есть два хранилища, которые позволяют хранить данные в формате ключ-значение: localStorage и sessionStorage. Их отличительная особенность в том, что данные сохраняются в браузере даже после обновления страницы. В случае с localStorage они останутся даже после перезапуска браузера.

Теоретически эти хранилища похожи на cookie — так же что-то хранят, так же в виде ключ-значения. Но есть важное отличие: cookie — это механизм хранения, с которым работает и сам браузер. Браузер сохраняет куки при получении соответствующих заголовков в ответах от сервера и отправляет куки вместе со всеми запросами на сервер. Данные же из localStorage и sessionStorage никак не связаны с запросами на сервер и не подставляются автоматически в каждый запрос. Поэтому если вы храните, например, JWT-токен в хранилище, то сами подставляйте его в запросы с помощью JavaScript.

Хранилища принадлежат точно так же, как и cookie: к домену, протоколу или порту. Такой подход позволяет не смешивать хранилища от разных приложений в одно общее «болото». С точки зрения безопасности: у мошенников меньше возможностей перехватить данные с других хранилищ пользователя, если удалось воспользоваться XSS.

Размер хранилища составляет как минимум 2 мегабайта. В настройках браузера можно выставить своё число. По умолчанию:

  • Chrome, Firefox и Opera ~ 5 МБ;
  • IE ~ 4,8 МБ;
  • iOS Safari, OS X Safari ~ 2,5 МБ;
  • Android ~ 5 МБ.

API у localStorage и sessionStorage одинаковое:

  • setItem(key: string, value: string) — сохраняет пару ключ-значение. Значение должно быть строкой, или оно будет автоматически преобразовано к строке. Потому стоит самим делать преобразование. Например, через JSON.stringify.
  • getItem(key: string) — получить данные по ключу.
  • removeItem(key: string) — удалить данные по ключу.
  • clear() — удалить всё.
  • key(index: number) — получить ключ на заданной позиции.
  • length — количество элементов в хранилище.

API очень напоминает интерфейс структур Map и Set.

Рассмотрим работу localStorage. Данное хранилище представляет собой единый объект на все вкладки в рамках единого источника (под единым источником подразумевается один и тот же домен, протокол, порт; о чём говорили в первом модуле). У данных нет expires, после которого всё очищается. Данные можно получить после перезагрузки браузера или даже всей операционной системы.

Примеры использования можно найти в «Современном учебнике JavaScript».

Основное, что нужно знать:

  • Можно добавить в значение любые данные, но всегда преобразуйте их в строку. В dev-консоли всё будет выглядеть нормально. Например, если это был объект, он будет показан как объект.
  • Не обращайтесь напрямую к свойствам, работайте с методами.
  • Для перебора используйте Object.keys или for..in с проверкой на hasOwnProperty.

У sessionStorage такое же API. Это хранилище отличается своим жизненным циклом, то есть доступно только в рамках текущей вкладки и сессии. Если перезагрузить страницу, данные будут сохранены. Но если перезагрузить браузер (не говоря уже про операционную систему), то данные в sessionStorage сотрутся. Учитывайте это.

Чаще используют localStorage, так как его срок жизни не ограничен. Однако могут быть случаи, когда долго хранить данные нерезонно. Например, если вы решили держать серверную сессию открытой только до закрытия браузера или выключения компьютера — sessionStorage ваш выбор, и при новом заходе на сайт надо будет заново авторизоваться.

Можно обрабатывать события изменения хранилища. То есть если ваше приложение (из любой вкладки браузера) поменяло данные в хранилище, то вы узнаете об этом:

// Срабатывает при обновлениях, сделанных в том же хранилище, но на других вкладках (это важно)
window.onstorage = event => { // Не забываем про addEventListener
  // Работает с event
};

localStorage.setItem('now', Date.now());

Такое отслеживание изменений может применяться как способ обмена данными между вкладками, но об этом расскажем дальше.

Cookie

Cookie — это уже знакомый вам механизм, описывать который заново не будем, но, как работать с ним на уровне JavaScript, покажем.

Важно: не используйте работу с cookie без необходимости. Если у вас есть доступ к пользовательским кукам с бэкенда без определённой цели, попросите бэкендеров добавить атрибут httpOnly (и тем более атрибут secure).

Для работы с cookie, в JavaScript используют свойство объекта document:

console.log(document.cookie); // name1=value1; name2=value2; ...

Значение данного свойства — это строка, которая состоит из пар ключ-значение, которые разделены через ;.

Запись в куки производится через простое присваивание:

document.cookie = 'userScore=1042';
console.log(document.cookie); // Будут отображены все куки

Вы можете также выставлять для них атрибуты. Для куки работают все те же правила, что и при получении или отправке по HTTP.

// Находясь на странице game.com,
// сделаем куки доступным для всех поддоменов *.game.com:
document.cookie = "userScore=1042; domain=site.com"

// позже

// на forum.game.com
console.log(document.cookie); // есть куки userScore=1042
