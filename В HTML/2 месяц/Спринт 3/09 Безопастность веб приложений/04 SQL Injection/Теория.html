SQL Injection

Инъекции — это уязвимости, направленные на возможность внедрения управляющего кода в язык запросов.

Инъекции бывают разные. Управляющий код можно вставить далеко не только в SQL-запрос:

  • SQL или NoSQL инъекции,
  • Command Injection,
  • CRLF-инъекции,
  • Parameter Contamination,
  • Path Traversal.

SQL инъекции

Рассмотрим простой пример работы с базой данных в Express:

const { id } = req.query;
// Просто подставляем пользовательский id
const sql = `SELECT * FROM chats WHERE id='${id}';`;
        
// Делаем GET /chats?id=123
// SELECT * FROM adventures WHERE id='123';

Вроде всё в порядке — получили ID, подставили и всё отлично. Но вдруг пользователь решил вставить в URL немного треша:

GET /chats?id=123asdf--1234

На что веб-сервер вернёт ошибку:

ERROR: invalid input syntax for type numeric: "PostgreSQL 8.2.13 on
i386-portbld-freebsd7.2, compiled by GCC cc (GCC) 4.2.1 20070719 [FreeBSD]"

Подобная информация сразу покажет злоумышленнику версию базы данных и что пошло не так. Он даже сможет узнать на какой строчке кода находится ошибка. Информация подобного рода позволяет злоумышленнику начать строить вектор атаки:

  • найти уязвимости данной версии и как можно их проэксплуатировать,
  • найти самое уязвимое место вашего сервиса.

Для начала — никогда не возвращайте в продакшн среде подробный стек-трейс ошибки. Если нет подробной клиентской ошибки, возвращайте пользователям просто “error”. А во внутренние логи компании или сервиса отправляйте стек-трейс, чтобы можно было быстро всё исправить или узнать, что не так.

Вернёмся к уязвимости. Злоумышленник пошёл дальше и решил попробовать запустить свой SQL-запрос через GET-параметр сервиса:

GET /chats?id=123' or '1'='1

К серверу отправляется ID 123. Так как наш сервер не валидирует значение, он подставит его в запрос к базе данных в таком же формате:

// Вот такое получится
const sql = `SELECT * FROM chats WHERE id='123' or '1'='1';`

То есть на выходе пользователю вернётся не информация по указанному чату, а список всех чатов и всей информации в таблице chats.

Исправить ситуацию можно следующим образом:

  1. санитайзить или эскейпить данные,
  2. использовать ORM,
  3. использовать prepared statement.

Эскейпинг помогает решить некоторые частные случаи атак:

const { name } = req.body;
const escaped = name.replace('\'', '\'\'');

const sql = `
  SELECT * FROM chats WHERE name='${escaped}';
`;

На OWASP можно подробнее прочитать об SQL Injection Bypassing WAF.

Руками эскейпить все вариации сложно, потому часто используют библиотеки для prepared statement.

Данная методология позволяет делать «подготовленные выражения», разделяя запрос от его логики данных. Подробнее можно почитать на:

  • Хабре,
  • PostgreSQL Prepared Statement.

Данный код позволяет соединить PREPARE у базы данных PostgreSQL и подготовить запрос в JS через механизм Prepared Statement.

PREPARE findChats (text) AS
  SELECT * FROM chats WHERE name = $1;
EXECUTE findChats('magic');

const { name } = req.body;

sequelize
  .query('SELECT * FROM chats WHERE name = :name', {
    replacements: { name },
    type: sequelize.QueryTypes.SELECT
  })
  .then(chats => res.send(chats));
