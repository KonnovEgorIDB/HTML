Что защищаем?

В веб-разработке нужно защищать каждый компонент сервиса:

  • frontend,
  • базу данных,
  • очереди событий,
  • сервера,
  • и всё остальное.

Если обобщить, мы должны защищать как client-side, так и server-side.

Уязвимости серверной части можно разделить на:

  • логические уязвимости — недочёты архитектуры,
  • ошибки эксплуатации — ошибки в администрировании,
  • ошибки реализации — ошибки в коде.

Логические уязвимости

Примеры логических уязвимостей:

  • отсутствие разграничений прав доступа у пользователей сервиса,
  • избыточная небезопасная функциональность,
  • нарушение логики работы приложения.

Секретный URL

Секретные урлы позволяют скрыть от всех пользователей реальные ID или путь. Любой пользователь может оказаться злоумышленником.

GET https://my-awesome-site.ru/admin

GET https://my-awesome-site.ru/aliSFla1434snf

Очевидный плюс — сокрытие информации.

Минусы:

  • урлы становятся длиннее,
  • пользователям сложно их читать и запоминать.

Однако даже такая функциональность может быть скомпрометирована. Вспомним утечку приватных страниц Google Sheet. У многих из них были секретные урлы и приватный доступ.

Нарушение логики и небезопасная функциональность

Рассмотрим пример оплаты на сайте интернет-магазина:

GET https://online-shop.ru/payment/step/1 // Выбираем способ оплаты
GET https://online-shop.ru/payment/step/2 // Производим оплату
GET https://online-shop.ru/payment/step/3 // Подтверждаем по СМС
GET https://online-shop.ru/payment/step/4 // Получаем товар

Если не проверять каждый шаг клиента, злоумышленник может обойти отдельные шаги и попытаться проэксплуатировать недочёты логики в сервере магазина.

Рассмотрим уязвимость “Insecure direct object reference”:

GET https://disk.yandex.ru/client/123

Допустим, у Яндекс.Диска все документы в URL определяются своим прямым ID из базы. Таким образом, любой человек может в цикле запустить загрузку файлов из всего сервиса. А значит, у злоумышленника получится выгрузить все публичные ресурсы и получить доступ ко всем файлам.

Сервер будет лишний раз полностью обслуживать клиента, выдавая полные ответы на каждый запрос с ID.

Даже крупные банковские системы были подвержены подобной уязвимости, не говоря о мессенджерах, где можно было по ID перебрать все сообщения.

Один из способов защититься — использовать хеши вместо ID. К хешу применяются все правила стойкости: подбор значения должен иметь полиномиальную вычислительной сложность.

GET https://disk.yandex.ru/client/1028379420

Теперь злоумышленнику будет сложно перебрать ресурсы сервиса. На невалидные запросы он будет получать быстрые ответы в виде 404.

Какие есть предпосылки к такой уязвимости? Ими могут быть:

  • сложности реализации,
  • плохо продуманная архитектура,
  • человеческий фактор.

Также от перебора защищаются при помощи установки rate limit на сервис. То есть ограничивают число запросов на пользователя с одного IP, ID и т. д.

Примеры сервисов, которые пользуются хешами:

  • Yandex-сервисы,
  • Google,
  • Miro,
  • Figma.

Примеры ошибок реализации проекта

  • инъекции,
  • гонки (или race conditions),
  • раскрытие информации,
  • плохая криптография,
  • бинарные уязвимости.
