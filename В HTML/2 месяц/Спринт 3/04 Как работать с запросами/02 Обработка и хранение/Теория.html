Обработка и хранение

Хранение

Компонентный подход позволяет логически отделить элементы пользовательского интерфейса друг от друга. Но возникает вопрос каким образом доставить в компоненты необходимые данные. Можно передавать их через пропсы вниз по дереву компонентов, но так как одни и те же данные нужны в разных частях приложения, это сделает код менее понятным и поддерживаемым.

Другой вариант — делать запрос каждый раз, когда потребовались те или иные данные, но такие запросы будут съедать время и трафик пользователя и сделают использование приложения неудобным.

Гораздо проще хранить все данные в одном глобальном хранилище. Доступ к нему из компонентов можно привязать к жизненному циклу так, чтобы нужные данные были доступны на этапе рендера. Часто такое хранилище называют состоянием приложения (application state).

Поток данных в приложении с глобальным состоянием часто выглядит вот так:

  1. Компонент запрашивает у контроллера данные.
  2. Контроллер делает запрос к API.
  3. Ответ от API контроллер кладёт в хранилище.
  4. Компонент забирает данные из хранилища и выводит пользователю.

Обработка

Сервис с API не должен сам куда-то класть данные. Вспомним принцип минимальной ответственности, атомарности — минимальная связность. API вообще не должен знать куда и что складывается или как обрабатывается.

Главная задача API — сделать запрос с нужными параметрами и в then вернуть полученный ответ.

Например, вот так лучше не делать, потому что появляется мусор, лишние связи и ненужная логика:

class UserAPI extends BaseAPI {
  create() {
	return api.post('/', {})
	  .then(data => someUpdate(data))
  	.then(data => someOtherChanges(data))
	  .then(data => moreLogic);
  }
}

Логику обработки данных стоит вынести в отдельную сущность под названием сервисы или контроллеры. Именно контроллеры вызываются внутри компонентов при запуске логики. Контроллер принимает решение делать запрос или нет и занимается обработкой полученных данных. Максимум, что можно делать в классе API, чтобы последний не превратился в многосвязный граф — это возврат только определённых свойств:

class UserAPI extends BaseAPI {
	create() {
		return api.post('/', {})
			// И то, только в случае, если уверены в результате,
			// иначе контроллер проверит все сам дальше
			.then({user: {info}} => info);
	}
}

Компонент не должен вызывать API. Всё должно происходить через контроллер.

Таким образом, можно получить большой прирост в скорости получения данных, их обработке и хранении.

Управлять состоянием приложения можно по-разному, обычно это зависит от общей архитектуры приложения и архитектуры данных. Например, для приложений на React чаще всего используют иммутабельное (не изменяемое) состояние и однонаправленный поток данных (Flux архитектура). Есть решения, где состояние мутабельное (изменяемое), а поток данных дву-направленный, например MobX. Подробнее с этим вы познакомитесь во втором модуле.

Реализуем мутабельное состояние, но при этом с однонаправленным потоком данных:

class Store {
  private state: Indexed = {};

  public getState() {
    return state;
  }

  public set(path: string, value: unknown) {
    set(this.state, path, value);
  };
}

Чтобы поддерживать однонаправленный поток, класс Store имеет два метода для изменения и получения данных: set и getState. Функция set устанавливает значение для объекта по указанному пути. Объект state изменяется, именно поэтому состояние мутабельное. Метод set вы реализуете в конце этого спринта вместе с другими утилитами, сейчас главное знать как он работает:

const state = {};

set(state, 'user.name', 'John'); 
console.log(state); // { user: { name: 'John' } }

Чтобы компоненты могли получать обновления при изменениях состояния, можно использовать уже знакомый паттерн EventBus. А чтобы объект состояния был глобальным, сразу экспортируем из модуля экземпляр класса — это ещё один способ реализовать синглтон паттерн в JavaScript:

export enum StoreEvents {
  Updated = 'updated',
}

// наследуем Store от EventBus, чтобы его методы были сразу доступны у экземпляра Store
class Store extends EventBus {
	...

  public set(path: string, value: unknown) {
    set(this.state, path, value);

		// метод EventBus
		this.emit(StoreEvents.Updated);
  };
}

export default new Store();

Теперь внутри компонента можно подписаться на обновления:

import store, { StoreEvents } from './store';

class UserProfile extends Block {
  constructor(...args) {
    super(...args);

		// запрашиваем данные у контроллера
		UserController.getUser();

		// подписываемся на событие
    store.on(StoreEvents.Updated, () => {
      // вызываем обновление компонента, передав данные из хранилища
      this.setProps(store.getState());
		});
  }

  render() {
    // внутри рендер в this.props будут достпны данные из хранилища
  }
}

При обновлении данных контроллером, компонент обновится, и пользователь увидит новые данные:

class UserController {
  public getUser() {
    UserAPI.getUser()
			 .then(data => store.set('user', data);
  }
}

Чтобы каждый раз в конструкторе компонента не подписываться на обновления состояния, можно реализовать компонент высшего порядка (higher-order component, HOC, по аналогии с функциями высшего порядка).

HOC — это функция, которая принимает в качестве аргумента компонент, а возвращает новый компонент с нужной логикой. Таким образом можно выделять одинаковую для нескольких компонентов логику, чтобы её было проще поддерживать в будущем:

function connect(Component: typeof Block) {
	// используем class expression
  return class extends Component {
    constructor(...args) {
			// не забываем передать все аргументы конструктора
      super(...args);

      // подписываемся на событие
	    store.on(StoreEvents.Updated, () => {
	      // вызываем обновление компонента, передав данные из хранилища
	      this.setProps({...store.getState()});
			});
    }
  } 
}

Теперь любой компонент можно обернуть в такой HOC, и он будет обновляться при изменениях данных. Использовать такой компонент можно так же, как и компонент без HOC — ничего дополнительно передавать не надо.

// UserProfile.ts
export connect(UserProfile);

// AccountPage.ts
const userProfile = new UserProfile();

Скорее всего, компоненту не нужны всё, что лежит в хранилище, поэтому в HOC можно передать функцию, которая выберет из состояния только нужные данные. Такая функция принимает состояние приложения в качестве аргумента, а возвращает объект с необходимыми полями.

function connect(Component: typeof Block, mapStateToProps: (state: Indexed) => Indexed) {
	// используем class expression
  return class extends Component {
    constructor(props) {
      super({...props, ...mapStateToProps(store.getState())});

      // подписываемся на событие
	    store.on(StoreEvents.Updated, () => {
	      // вызываем обновление компонента, передав данные из хранилища
	      this.setProps({...mapStateToProps(store.getState())});
			});
    }
  } 
}

function mapUserToProps(state) {
  return {
    name: state.user.name,
    avatar: state.user.avatar,
  };
}

connect(UserProfile, mapUserToProps);

Иногда в два разных компонента нужно передать одинаковые данные из состояния, поэтому будет удобнее использовать каррирование. Таким образом можно создать компонент высшего порядка для определенных данных, а затем обернуть в него любые другие компоненты:

function connect(mapStateToProps: (state: Indexed) => Indexed) {
  return function(Component: typeof Block) {
    return class extends Component {
      ...
    }
	}
}

const withUser = connect(state => ({ user: state.user }));

withUser(UserProfile);
withUser(SettingsPage);
