Переходы

Вы сделали много страниц и знаете, что одновременно активна только одна из них (вью). Но как обеспечить удобный переход между ними? Например, прописать логику, согласно которой каждая вью будет скрывать себя и вызывать соседа. Вскоре получим вот такую картину:

На рисунке всего несколько вьюшек, но уже сложно отслеживать их перемещения. А если у блока или страницы поменяется API, ошибки неизбежны.

На помощь приходит паттерн «Медиатор», о котором говорили ранее. Таким медиатором станет роутер. Он получит доступ к API у страниц, узнает какие страницы какому URL соответствуют и будет решать — на каких URL какие страницы отображать.

Было бы ошибкой хранить в приложении информацию о том, какая страница сейчас отображается. Для этого лучше использовать роутер и роутинг. Ему одному достаточно знать, что, например, по адресу /user следует отображать страницу пользователя. Также роутер интегрируется с API браузера и позволит получить ожидаемое поведение — при клике на кнопку «Назад» в браузере будет отображена предыдущая страница.

Различают серверный и клиентский роутинг.

Серверный роутинг — это процесс определения маршрута внутри приложения в зависимости от запроса. Проще говоря, это поиск контроллера по запрошенному URL и выполнение соответствующих действий.

То есть серверный роутинг — это соответствие между запросом и тем, какие данные вернёт сервер.

Клиентский роутинг в современных фронтенд-приложениях — это соответствие между адресной строкой браузера и блоком (страницей, вью), который будет отображаться. Код на JS имеет доступ к адресной строке браузера, извлекает из неё необходимые данные и на основе этого вызывает render (или какой-нибудь другой код в приложении), который отобразит на экран нужный блок.

Помимо всего прочего, роутеры эмулируют историю переходов по страницам в SPA-приложениях.

Взаимодействие и переключение между страницами происходит благодаря роутеру. Мы убрали уровень связанности между страницами, и теперь все страницы будут знать только о роутере, а не друг о друге. Это делает проект более гибким и масштабируемым.

Представим, как можно было бы пользоваться пока воображаемым роутером:

Router.use({state: 'main'}, MainBlock);
Router.use({state: 'signup'}, SignupBlock);
Router.use({state: 'chats'}, ChatsBlock);

...

// переход на третью страницу (пагинация)
Router.go({state: 'chats', params: {page: 3}});

Примерно такой API роутера был бы удобен для программиста:

class Router {
  constructor() { ... }
  use(path: string, block: Block) { ... }
  start() { ... }      // запустить роутер
  go(path: string) { ... }
  back() { ... }       // переход назад по истории браузера
  forward() { ... }    // переход вперёд по истории браузера
}
