Пишем тесты

Советы

Пара небольших советов, которые помогут писать эффективные и красивые тесты.

Правильно их описывайте и структурируйте

Не стоит дублировать название группы тестов в каждом отдельном тест-кейсе данного дерева. Кроме того, не стоит группировать не связанные по логике тест-кейсы (например, вы проверяете авторизацию, а в одном из тест-кейсов рядом решили проверить утилиту). Вот так делать не стоит:

describe('Авторизация', () => {
  it('Авторизация должна уметь в signin', () => {
  });

  it('Авторизация должна уметь в signup', () => {
  });

  it('Авторизация должна уметь в logout', () => {
  });

  it('Что-то дополнительно связанное с авторизацией', () => {
  });
});

Вместо такого дерева можно сделать немного иное:

describe('Авторизация', () => {
  it('Проверяем корректный logout', () => {
  });

  describe('Проверка авторизации через форму', () => {
    it('Проверяем валидные данные в signin', () => {
    });

    it('Проверяем валидные данные в signup', () => {
    });
  });

  describe('Дополнительный функционал при авторизации', () => {
    it('Что-то дополнительно связанное с авторизацией', () => {
    });
  });
});

Тесты пишутся не только, чтобы проверить функционал, но также, чтобы их читали ваши коллеги. Вы пишете и для них в том числе (как и весь другой код в проекте). Не стоит пренебрегать качеством описания тестов.

Не комментируйте тесты

Never. Ever.

Не нужно комментировать тесты, потому что они долгие или ресурсоёмкие. Тесты также стоит декомпозировать и делать лёгкими.

Не стоит делать, как в этом забавном видео (не удаляйте тесты). Если это выстрелило даже у вас, значит, по Закону Мёрфи, выстрелит и у пользователя. Вероятно, в самый неподходящий момент.

Избегайте логики в тестах

Используйте простые выражения. Не используйте циклы или условия. Если вы это добавите, то примете риск, что появится новая потенциальная ошибка в самом тесте.

При добавлении условий вы не знаете, по какому пути пойдёт тест. И каждый тест будет неопределённым поведением с возможностью пропустить в продакшн код с багом.

При добавлении цикла вы не упрощаете себе жизнь, а делаете так, что не можете разделять состояния между тест-кейсами. Автоматизация в данном случае вредна (кроме частных случаев, которые легко обговариваются).

it('что-то проверяем', () => {
  const testValues = {
	'Выход 1'         : 'Вход 1',
	'Выход 2'         : 'Вход 2',
	...
  };

  for (let result in testValues) {
    expect(mySuperFunc(testValues[result])).toBe(result);
  }
});

Избавившись от циклов, ваши тест-кейсы станут легче, будут проходить быстрее и также будут логически верно разбиты заголовками:

it('что-то проверяем', () => {
  expect(mySuperFunc('Вход 1')).toBe('Выход 1');
  expect(mySuperFunc('Вход 2')).toBe('Выход 2');
});

А можно сделать совсем хорошо. Давайте разобьём на разные тест-кейсы, ведь мы пишем код для коллег:

it('конкретно описываем, что проверяем', () => {
  expect(mySuperFunc('Вход 1')).toBe('Выход 1');
});

it('конкретно описываем, что проверяем', () => {
  expect(mySuperFunc('Вход 2')).toBe('Выход 2');
});

Используйте Фабрики

Паттерн «Фабрика» поможет писать тесты таким образом, чтобы:

  • можно было уменьшить настройку тестов (before, beforeEach, …);
  • каждый тест стал более читабельным (улучшает в том числе DRY);
  • обеспечить гибкость при создании новых экземпляров сущностей.

Пример без Фабрики:

describe('Что-то про MyEntity', () => {
  let myEntity;

  beforeEach(() => {
    myEntity = new MyEntity({...});
  });

  it('что-то проверяем', () => {
		...
		myEntity.someMethod();
		...
  });

  it('что-то ещё проверяем', () => {
		...
		myEntity.someOtherMethod();
		myEntity.someOtherOtherMethod();
		...
  });
});

Пример с Фабрикой:

describe('Что-то про MyEntity', () => {
	function createEntity({...options}) {
		return new MyEntity({...options});
	}

  it('что-то проверяем', () => {
		const myEntity = createEntity({...});

		...
		myEntity.someMethod();
		...
  });

  it('что-то ещё проверяем', () => {
		const myEntity = createEntity({...});

		...
		myEntity.someOtherMethod();
		myEntity.someOtherOtherMethod();
		...
  });
});

Теперь тесты стали более читабельными и простыми. То есть не нужно думать, «а есть ли выше beforeEach, от которого зависит кейс?». Теперь кейс стал прозрачным и «плоским».

Не используйте единый тест для всех кейсов

Если какой-то метод возвращает разные результаты при разных входных данных, не проверяйте всё в одном кейсе. Если где-то «выстрелит» баг, будет проще понять, на каких входных данных падает, нежели получить ошибку «упало в кейсе <проверить всё> на строчке N, символ K»:

// Не стоит делать так

it('проверить всё', () => {
  // expect(...).to(...);
  // expect(...).to(...);
});

// Стоит делать так

it('функция должна обработать такие-то данные', () => {
  // expect(...).to(...);
});

it('функция должна не упасть на таких-то данных', () => {
  // expect(...).to(...);
});
