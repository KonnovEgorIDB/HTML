Объединение типов

Есть много причин полюбить TypeScript. Если вы их ещё не нашли, вот несколько примеров:

  • Спасёт от выстрелов в ногу (в первую очередь в вашу).
  • ESNext здесь и сейчас и компиляция в нужную версию ES.
  • Подсказка нужных типов и поддержание крупного проекта в «типобезопасности».
  • Средство против TypeError.
  • Возможность проектировать «от интерфейса».
  • Документация к коду.

Но любовь — это не всегда только радость. Здесь так же, ведь кода стало намного больше и писать его дольше. Однако TypeScript умный, и на помощь приходит вывод типов, который позволяет иногда не указывать типы явно.

Но на одних простых типах далеко не уехать, поэтому дальше рассмотрим возможности работы с системой типов.

Union types

Что делать, если переменная, аргумент или возвращаемое значение могут быть несколькими типами в зависимости от обстоятельств? Возьмём метод split — он умеет разбивать строку по указанному разделителю. Разделителем, в свою очередь, может быть как строка, так и регулярное выражение. Составить такой тип поможет механизм union types:

// String.split
split(separator: string | RegExp, limit: number): string[]

В этом примере разделителем может быть либо строка, либо регулярное выражение. На другие типы данных компилятор будет ругаться.

При определённой настройке tsconfig объединение типов позволяет сразу корректно проектировать классы. Посмотрите на этот пример:

class Dog {
  name: string;
}

TypeScript покажет ошибку на поле name:

Property 'name' has no initializer and is not definitely assigned in the constructor.(2564)

Это значит, что сейчас класс не до конца честен с программистом: поле объявлено как string, но по факту в нём undefined, и если не задать поле в конструкторе или при объявлении, то TypeScript логично считает это объявление типа некорректным.

Таким образом, вы должны задуматься над тем, как привести поле в порядок: либо добавить ему начальное значение при объявлении или в конструкторе, либо изменить тип, чтобы он был честным:

// Пометить поле ?
class Dog {
  name?: string;
}

// Или явно указать тип
class Dog {
  name: string | undefined;
}

Также бывает, что функции проектируются под возврат значения или ошибки. В этом случае тоже помогает union type:

type Result = { value: string; };
type Error = { code: number; message: string; };

// Эта функция возвращает результат или ошибку, и это явно описано
function calculateSomething(): Result | Error {
	// ...
}

Intersection types

Кроме операции объединения, есть также операция пересечения типов. Она отличается тем, что объединяет несколько типов в один, суммирует их. То есть переменной может быть присвоено только то значение, которое принадлежит ко всем перечисленным типам.

Представим, что есть тип «Кошка» и тип «Собака». Если применить пересечение, то получим «Котопёс». Любой зверь уже не подойдёт, он должен быть и кошкой, и собакой одновременно. А если бы мы использовали объединение, то подошёл бы только один из них. Вот такая зоология.

type Cat = {
  purr(): void;
}

type Dog = {
  woof(): void;
}

type CatDog = Cat & Dog;

// Ошибка
// Type '{ purr(): void; }' is not assignable to type 'CatDog'.
//  Property 'woof' is missing in type '{ purr(): void; }' but required in type 'Dog'.
const animal1: CatDog = {
	purr() { /**/ }
}

// Теперь всё хорошо, объект соответствует всем полям из типа
const animal2: CatDog = {
	purr() { /**/ },
	woof() { /**/ }
}

Также стоит отметить, что не стоит пересекать типы с одинаковыми полями — это приведёт к ошибкам:

type Cat = {
  purr(): void;
  name: string;
}

type Dog = {
  woof(): void;
  name: Symbol;
}

type CatDog = Cat & Dog;

const animal1: CatDog = {
	purr() {},
	// Error: Type 'string' is not assignable to type 'string & Symbol'.
  name: 'doggy',
  woof() {}
}

Type alias

У объединения типов есть проблема. Иногда его результат приходится часто переиспользовать, что приводит к лишнему копированию кода (нарушению принципа DRY). Если у родителя изменится тип, его придётся менять во всём проекте. Это противоречит слабой связности, описанной в темах про архитектуру:

split(separator: string | RegExp, limit: number): string[]

const data: string | RegExp = ...;
...
split(data, ...);

Если добавим, например, новый тип null, во всём проекте придётся добавить null. Иначе типы будут не совпадать: string | RegExp против string | RegExp | null. А если решите, например, убрать ещё и string? Снова море рутинной работы. Поэтому объединения лучше выносить в общие типы.

Type aliases решат проблему архитектурно. Перепишем метод split с их использованием:

type StringOrRegExp = string | RegExp

split(separator: StringOrRegExp, limit: number): string[]

Также можно писать синонимы на стандартные типы:

type UserName = string

interface User {
	name: UserName;
}

Код станет проще поддерживать, а вы сэкономите драгоценные минуты для более важных свершений.

Literal types

Алиасы типов могут принимать не только типы, но и значения. Лучше один раз показать:

// String literal type
type NameStr = 'name';

// ok
const name1: NameStr = 'name';

// Type '"wow!"' is not assignable to type '"name"'
const name2: NameStr = 'wow!';

// Number literal type
type Two = 2;

// ok
const val1: Two = 2;

// Type '1' is not assignable to type '2'
const val2: Two = 1;

// Boolean literal type
type True = true;

// ok
const b1: True = true;

// Type 'false' is not assignable to type 'true'
const b2: True = false;

То есть можно создать тип конкретного значения, и ничего кроме этого значения нельзя будет положить в переменную этого типа.

К literal types можно применять операцию объединения типов (type union):

type CatOrDog = 'cat' | 'dog';

type CatDogAnimal = {
	type: CatOrDog;
}

const cat: CatOrDogAnimal = { type: 'cat' };
const dog: CatOrDogAnimal = { type: 'dog' };
// Error: Type '"bird"' is not assignable to type 'CatOrDog'
const bird: CatOrDogAnimal = { type: 'bird' };

Discriminating unions

Бывает так, что нужен набор типов, которые в целом похожи, входят в одно семейство (имеют одно назначение), но все они немного разные. Представьте функцию, которая делает запрос на сервер и может возвратить значение несколькими способами (ну вот так придумали разработчики): просто значение из кэша, промис со значением, Observable со значением. Можно написать так:

type Observable<T> = {
	listen(cb: (value: T) => unknown): VoidFunction;
};

function requestData<T>(): T | Promise<T> | Observable<T> { /**/ }

const result = requestData<string>();

И как теперь этой функцией пользоваться? Как определять, какой тип данных вернулся? Здесь, конечно, помогут type guard, которые могут проверить значение. Но так как функция возвращает тип дженерика, понять, что вернулся именно этот чистый тип, а не Promise или Observable, будет сложнее. Да и красиво отличить Promise от Observable не получится — придётся лезть в их «внутренности» и проверять, например, наличие методов then или listen:

function isPromise<T>(value: unknown): value is Promise<T> {
	return typeof (value as any).then === 'function';
}

Хочется иметь инструмент, который позволит явно и чисто отличать типы. И тут на помощь приходит discriminating unions — приём, когда мы объединяем несколько типов, содержащих одинаковое поле. Плюс добавим к этому literal types:

type RawValue<T> = {
	type: 'raw';
	value: T;
};

type PromiseValue<T> = {
	type: 'promise';
	value: Promise<T>;
};

type ObservableValue<T> = {
	type: 'observable';
	value: Observable<T>;
}

type RequestValue<T> = 
	| RawValue<T>
	| PromiseValue<T>
	| ObservableValue<T>;

function requestData<T>(): RequestValue<T> { /**/ }

Теперь понять тип полученного значения легко:

// Три type guard

function isRawValue<T>(value: RequestValue<T>): value is RawValue<T> {
	return value.type === 'raw';
}

function isPromiseValue<T>(value: RequestValue<T>): value is PromiseValue<T> {
	return value.type === 'promise';
}

function isObservableValue<T>(value: RequestValue<T>): value is ObservableValue<T> {
	return value.type === 'observable';
}

const response = requestData<number>();

if (isRawValue(response)) {	
	// response.value сейчас number
  console.log(response.value);
} else if (isPromiseValue(response)) {
	// response.value сейчас Promise<number>
  response.value.then(console.log);
} else if (isObservableValue(response)) {
	// response.value сейчас Observable<number>
  response.value.listen(console.log);
}

Type и interface

Одну и ту же структуру данных можно описать как в type alias, так и в интерфейсе:

type Point = {
  x: number
  y: number
}

interface Point {
  x: number
  y: number
}

Алиасы не заменяют интерфейсы. Всё зависит от целей.

Интерфейс — это создание новой сущности, в то время как алиас создаёт для типа новое имя. Отличия алиаса от интерфейса:

Ниже список операций над типами, которые ещё называют «множествами»:

  • объединение типов |,
  • пересечение типов &,
  • вычитание одного типа из другого (сюда относятся, например, Exclude и Omit).

В заключение стоит сказать, что тема выбора «interface или type» достаточно «холиварная»: всё, что можно сделать с помощью interface, можно сделать и с помощью type. И не всё, что можно сделать с помощью type, можно сделать с помощью interface. В следующем уроке вы в этом убедитесь.
