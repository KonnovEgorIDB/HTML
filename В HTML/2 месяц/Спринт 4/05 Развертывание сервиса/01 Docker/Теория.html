Введение в проблему

Для запуска вашего приложения может потребоваться множество вещей:

  • pm2 или ts-node для того, чтобы запустить приложение на JS/TS;
  • nginx для того, чтобы корректно раздавать статику и управлять CORS, кэшированием и HTTP/2;
  • PostgreSQL или MySQL как реляционная база данных;
  • MongoDB как нереляционная база данных;
  • Redis или Memcache для кэширования данных;
  • Cron для запланированных задач;
  • и прочие полезные вещи.

Если все это поставить на ваш рабочий компьютер — начнётся кошмар. Особенно если вы работаете над несколькими проектами. Один проект, например, требует определённую версию Node, другой проект — иную. Какому-то проекту нужна одна база данных, другому — другая, третьему обе базы сразу и других версий (такое тоже бывает). В течение короткого времени ваш чистый рабочий компьютер будет завален программами и сервисами, которые не нужны в каждый момент времени, но они просто есть и тратят ресурсы. А ещё все эти программы замусоривают вашу операционную систему, вызывая неожиданные проблемы и конфликты при установке новых программ. Ситуация может усугубиться настолько, что придётся переустанавливать ОС.

Как было бы здорово, если при работе с проектом понадобится база данных, а мы бы её запустили в каком-то ограниченном от основной операционной системы пространстве, поработали, выключили и забыли, сохранив чистоту нашего компьютера. Такой способ есть — контейнеризация.

Контейнеризация

Контейнеризация — метод виртуализации, при котором ядро операционной системы поддерживает несколько изолированных экземпляров пространства пользователя вместо одного. Эти экземпляры (обычно называемые контейнерами или зонами) с точки зрения пользователя полностью идентичны отдельному экземпляру операционной системы.

Проще говоря — в вашей операционной системе запускается ещё одна, обособленная операционная система (и может быть даже не одна), и вы можете с ней взаимодействовать. А когда она становится не нужна — выключаете её и удаляете. Красота!

Docker

Самый популярный на сегодня инструмент для контейнеризации — Docker. Скачайте его с официального сайта, установите и запустите. На Windows придется пошаманить, вот инструкция. Если не хочется шаманить с Windows (нужна Windows 10 выше определенной версии) — можно установить Docker на вашу виртуальную машину в облаке, и проводить действия там. Инструкция по установке докера в Ubuntu.

Docker — это набор программного обеспечения, позволяющий легко описывать контейнеры, запускать и останавливать их, связывать друг с другом, удалять, поддерживать их работу и многое другое. Алгоритм работы с Docker состоит из нескольких шагов:

  1. Описать настройки контейнера — какая в нём будет операционная система, какие программы туда будут установлены, какие команды должны выполниться при старте операционной системы.
  2. Собрать (build) контейнер из описания настроек (на жёстком диске компьютера контейнер представлен файлами — там будут файлы операционной системы, программ и прочее).
  3. Запустить (run) контейнер, который был собран.
  4. Остановить запущенный контейнер.
  5. Удалить контейнер, чтобы больше не занимал место на диске.

Шаги 3 и 4 можно повторять до тех пор, пока контейнер вам нужен в работе. Отвлеклись от одного проекта и перешли к другому? Просто остановите контейнер, а когда понадобится — снова включите. Сдали проект и больше контейнер не нужен? Удаляйте его.

Теперь посмотрим как сделать все эти шаги и запустим наш первый контейнер с простейшим приложением на NodeJS, вот таким:

const http = require('http');

const hostname = '0.0.0.0'; // сервер запустим на всех интерфейсах
const port = 3000;

const server = http.createServer((req, res) => {
  res.statusCode = 200;
  res.setHeader('Content-Type', 'text/plain');
  res.end('Hello World');
});

server.listen(port, hostname, () => {
  console.log(`Server running at http://${hostname}:${port}/`);
});

Запакуем его в контейнер, где оно сможет запускаться даже без NodeJS на вашем компьютере. А пока сохраните его в какую-нибудь папку.

Кофигурация и запуск докера

Конфигурация контейнера для Docker описывается в файле с именем Dockerfile. Создайте его рядом с JS-файлом.

Полную документацию по написанию Dockerfile можно найти на официальном сайте, а мы пройдёмся по основным командам.

FROM

Каждый контейнер должен иметь операционную систему. Одни из самых распространенных систем — Alpine, Ubuntu и Debian. Alpine — это очень маленький (буквально 5Мб) линукс. В нём нет почти ничего, кроме ядра и командной строки. Ubuntu и Debian побольше, в них есть всё нужное для работы.

Описанный однажды Dockerfile называется образом. Множество готовых образов можно найти на Docker Hub и не писать их самостоятельно. Но сейчас в учебных целях создадим свой образ.

Команда FROM обозначает, какой образ какой версии надо взять за основу вашего контейнера. Синтаксис команды: FROM %BASE%:%VERSION%. %BASE% — имя образа, %VERSION% — версия. Версия может быть конкретной, например 18.3, а может быть последней, что обозначается latest.

Хотите чтобы там была Ubuntu? Пишете FROM ubuntu:latest. Контейнер будет запускать Ubuntu последней версии. Хотите специфичную версию — пишите FROM ubuntu:18.04.

Запишем эту команду в Dockerfile:

FROM ubuntu:18.04

Сейчас уже можно попробовать собрать ваш контейнер. Для этого перейдите в терминале в папку, где лежит Dockerfile и скрипт простого сервера, и введите docker build -t lesson ..

RUN

Поставить одну операционную систему недостаточно — нужно установить в неё необходимый софт. В нашем случае это NodeJS.

В процессе сборки образа Docker может запустить команды, которые мы можем прописать в Dockerfile. Для этого используется команда RUN. Синтаксис RUN ..., где троеточие означает любую валидную операцию в командной строке. Давайте установим NodeJS:

FROM ubuntu:18.04
RUN apt update && apt install -y nodejs && apt install -y npm

Здесь мы указали докеру запустить три команды — обновить репозиторий пакетов, установить NodeJS и установить npm (просто на закуску).

Опять соберём контейнер: docker build -t lesson .

CMD

Эта команда выполнится, когда контейнер будет запущен (о запуске поговорим через мгновение). В этом принципиальная разница с командой RUN — та запускается на этапе сборки.

Пока выполним простейшее действие — вывод версии NodeJS. Пропишем в Dockerfile новую строку:

FROM ubuntu:18.04
RUN apt update && apt install -y nodejs && apt install -y npm
CMD node -v

Синтаксис такой же, как у команды RUN. Не забудьте пересобрать контейнер.

Первый запуск контейнера

Убедимся, что наш контейнер получился рабочим. Для этого его надо запустить.

Запуск в самом простом виде производится командой docker run lesson. Синтаксис docker run %имя образа%. Запустите команду и увидите что-то подобное:

% docker run lesson       
v8.10.0

Отлично, команда запустилась и вывела в консоль версию ноды (древнюю в данном случае). Пришло время запустить в контейнере наш скрипт.

COPY и WORKDIR

Сейчас файл с простейшим сервером лежит просто рядом с докерфайлом и никак не попадает в контейнер. Контейнер изолирован от нашей операционной системы и её файловой системы. Надо скрипт как-то поместить в контейнер на этапе сборки, чтобы контейнер получился уже с нашим скриптом. А для того, чтобы поместить скрипт в предсказуемое место в контейнере используем команду WORKDIR.

Команда WORKDIR указывает контейнеру, куда нужно сделать команду cd внутри контейнера при сборке и запуске контейнера. Изменим Dockerfile, уберём CMD с версией ноды и допишем пару команд:

FROM ubuntu:18.04
RUN apt update && apt install -y nodejs && apt install -y npm
WORKDIR /var/www
COPY ./simpleServer.js simpleServer.js
CMD echo $PWD && ls -la && cat simpleServer.js

Во-первых, мы указали докеру, что всю работу надо проводить в папке /var/www. Во-вторых, использовали команду COPY. Её синтаксис: COPY %local file% %container file%. В нашем случае скрипт назывался simpleServer.js, и докеру было сказано скопировать его в файл simpleServer.js. А так как действие происходит в папке /var/www — файл скопируется именно в неё.

Не забыли пересобрать контейнер после внесённых изменений?

Чтобы убедиться, что файл скопировался правильно, мы изменили команду CMD, чтобы она вывела текущую директорию, список файлов в ней и вывела содержимое скрипта. При запуске контейнера вывод должен быть таким:

Запуск Docker в фоновом процессе, остановка и мониторинг

Каждый раз, когда мы запускали контейнер — срабатывала та команда, что прописана в CMD и контейнер останавливался, а управление терминалом возвращалось к нам. Прежде чем перейти к запуску нашего простейшего сервера в докере надо научиться запускать Docker в фоне, следить за запущенными контейнерами и останавливать их при надобности.

Чтобы запустить контейнер в фоновом режиме, достаточно написать флаг -d при запуске: docker run -d lesson. Контейнер запустится, в терминал будет выведен идентификатор запущенного процесса и управление консолью снова будет в нашем распоряжении.

Чтобы посмотреть, какие контейнеры сейчас запущены, надо воспользоваться командой docker ps, и она выведет список контейнеров с их идентификаторами, именами и прочей информацией. Примерно вот так:

% docker ps
CONTAINER ID   IMAGE     COMMAND                  CREATED          STATUS          PORTS     NAMES
ed22504503c2   lesson    "/bin/sh -c 'node si…"   33 seconds ago   Up 30 seconds             sleepy_yonath

И наконец остановка контейнера: docker stop -t 0 ed22. Основная команда docker stop, далее параметр -t 0, говорящий докеру остановить контейнер немедленно (t значит “timeout”), и в конце начальные буквы идентификатора контейнера — не обязательно перепечатывать всё значение, достаточно первых уникальных символов.

Запуск node-сервера в контейнере

Теперь, когда мы вооружены знанием о запуске, мониторинге и остановке контейнеров, можно запустить приложение на ноде в контейнере и надеяться на результат (кстати, убедитесь, что этот скрипт работает: запустите и посмотрите ответ в браузере на localhost:3000, а затем остановите запущенный скрипт).

Изменим команду запуска:

FROM ubuntu:18.04
RUN apt update && apt install -y nodejs && apt install -y npm
WORKDIR /var/www
COPY ./simpleServer.js simpleServer.js
CMD node simpleServer.js

Самостоятельная работа: пересоберите образ и запустите его в фоне. docker ps при этом должен сообщить вам, что контейнер запущен и функционирует.

Теперь попробуйте зайти в браузере на localhost:3000, ничего не выйдет. Почему так? Ведь контейнер запущен, в нём запущен сервер на ноде — где деньги, Лебовски?

Проброс портов

Всё, что происходит в контейнере — остаётся в контейнере. Внутри контейнера действительно занят порт 3000, и там по нему будет отвечать веб-сервер. Но снаружи контейнер — это чёрный ящик, о котором мы ничего не знаем. Для связи нашей операционной системы (она называется хостом) с контейнером служат два механизма: проброс портов и проброс файловой системы. Начнём с первого.

Нам надо указать в Dockerfile, чтобы Docker открыл доступ к определенным портам. Делается это с помощью команды EXPOSE %N%, где N — номер порта. Допишем в Dockerfile:

FROM ubuntu:18.04
RUN apt update && apt install -y nodejs && apt install -y npm
WORKDIR /var/www
COPY ./simpleServer.js simpleServer.js
EXPOSE 3000
CMD node simpleServer.js

Остановим и пересоберём контейнер, а затем снова запустим. Но в браузере по прежнему ничего не увидим. Потому что недостаточно описать только EXPOSE, надо и при старте контейнера указать докеру заняться портами.

Сделать это можно с помощью ключа -p.

-p — ключ, которому надо указать порты: порт в хостовой системе и порт в контейнере. Docker их свяжет. docker run -p %HOST_PORT%:%CONTAINER_PORT%. Например, хотим чтобы 3000 порт из контейнера был доступен в хост-системе на 4000 порту. Для этого запуск будет таким: docker run -p 4000:3000 -d lesson.

Теперь всё должно заработать. Запись EXPOSE в Dockerfile носит информационный характер и сообщает пользователю Dockerfile об используемых в приложении портах, чтобы он знал, что указывать в -p.

Проброс файловой системы

Дать контейнеру доступ к хостовой файловой системе — очень полезное свойство докера. Контейнеры абсолютно изолированы от нашей системы, и при выключении всё, что происходило в контейнере исчезает. Например, мы запустим MongoDB в контейнере. MongoDB хранит свои данные в файлах, что очевидно. 🙂 При старте контейнера файлы будут созданы, вы поработаете с базой, а потом выключите контейнер. И все данные сотрутся. Чтобы такого не происходило, придумали проброс файловой системы, когда мы можем папку с хоста «примонтировать» в какую-то папку в контейнере. Освоим этот навык.

Для этого первым делом модифицируем скрипт и файловую структуру. Создайте рядом со скриптом и Dockerfile папку shared (название может быть любое), и положите в неё какой-нибудь текстовый файл, например text.json.

Теперь изменим скрипт, чтобы он при получении запроса читал данные из этого файла text.json и отдавал в ответе:

const http = require('http');
const fs = require('fs');

const hostname = '0.0.0.0'; // сервер запустим на всех интерфейсах
const port = 3000;

const server = http.createServer((req, res) => {
	const sharedValue = fs.readFileSync('./shared/text.json');
  res.statusCode = 200;
  res.setHeader('Content-Type', 'text/plain');
  res.end('Hello World' + sharedValue);
});

server.listen(port, hostname, () => {
  console.log(`Server running at http://${hostname}:${port}/`);
});

Пересобираем контейнер.

Теперь надо папку shared примонтировать в контейнер. Делается это с помощью ключа -v при запуске контейнера: docker run -v %HOST_ABSOLUTE_PATH%:%CONTAINER_ABSOLUTE_PATH%. Например docker run -v ~/Documents/Code/docker_lesson/shared:/var/www/shared. У вас до двоеточия будет путь в вашей файловой системе. Не забудьте про остальные аргументы запуска (порты, запуск в фоне, имя образа) и запустите контейнер. Посмотрите на ответ сервера. Потом поменяйте содержимое файла text.json и снова посмотрите на ответ сервера — он изменился. Потому что файлы, которые вы поменяли в вашей операционной системе в папке shared доступны и в контейнере.

Проброс файловой системы применяют тогда, когда данные контейнера надо сохранить. Для этого выясняют, где в контейнере приложение хранит свои данные, и пробрасывают туда локальную папку из проекта. Содержимое пробрасываемых папок обязательно добавляют в .gitignore, оставляя в них только файл .gitkeep, чтобы не возникло приключений с отсутствующими папками (попробуйте прокинуть в контейнер папку, которой не существует на хосте, будет ошибка).
