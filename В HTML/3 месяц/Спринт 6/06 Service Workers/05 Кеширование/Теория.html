Кеширование

Вот мы и подошли к самому интересному. В этом уроке покажем пример кеширования с помощью Service Worker.

Начнём с подготовительных работ. Для начала нужно создать константу с именем кеша. Используя этот ключ, будем добавлять и доставать кеш.

const CACHE_NAME = 'my-site-cache-v1';

Советуем использовать версионирование в названии для возможных будущих обновлений (например, если нужно удалить из браузера старый кеш и использовать новый).

Далее необходимо создать массив с валидными урлами до статики:

const URLS = [
	'/',
	'/application.tsx',
	'/index.tsx',
	...
];

Обратите внимание, что если хотя бы один URL будет ошибочным — кеш не будет создан для всех урлов.

По этой причине самый простой способ — это каждый раз руками гарантировать корректность нужной статики. Но что если она динамически меняется с каждой выкладкой?

Есть много способов динамической подстановки путей: через Webpack, через NodeJS, смешанные. Попробуйте найти их в интернете и поэксперементировать или даже придумать свой способ. Это может пригодиться вам в проектной работе.

Теперь закешируем статику нашего ресурса в уже знакомом обработчике жизненного цикла install:

this.addEventListener("install", event => {
	event.waitUntil(
		caches.open(CACHE_NAME)
		.then(cache => {
		  console.log("Opened cache");
		  return cache.addAll(URLS);
		})
		.catch(err => { 
	      console.log(err);
		  throw err;
		})
	);
});

Разберём этот код подробнее. В callback события install мы получаем event, который предоставляет нам API по работе с текущим экземпляром SW. Мы используем метод waitUntil, который гарантирует, что установка SW не завершится, пока промис в качестве аргумента метода не будет зарезолвен.

В качестве аргумента мы используем цепочку промисов. Для начала мы получаем доступ к кешу по имени (константа CACHE_NAME) с помощью метода open. В результате выполнения этого промиса получим экземпляр cache. Его можно использовать для записи и чтения кеша. В нашем случае мы используем метод addAll объекта cache для кеширования всей указанной статики.

Обратите внимание, что на этом этапе SW сделает запрос на каждый указанный URL и ответ он положит в кеш.

Отлично, статику закешировали, но что делать с запросами на сервер? Для этого в SW есть событие fetch:

this.addEventListener("fetch", event => { 
 // Код
});

Каждый запрос к серверу будет проходить через этот обработчик. Именно в этом месте мы сможем настроить программированное кеширование запросов.

Начнём с метода respondWith объекта event:

this.addEventListener("fetch", event => {
	event.respondWith();
});

Этот метод принимает в себя промис, который получит основной поток выполнения JS-кода.

Самое время определиться со стратегией кеширования. В данном примере воспользуемся стратегией “cache-only”. Если данные в кеше есть — выдаём в основной поток кеш, в противном случае делаем запрос на сервер, а результат возвращаем в основной поток и кладём в кеш.

this.addEventListener('fetch', event => { 
	event.respondWith( 
		// Пытаемся найти ответ на такой запрос в кеше 
		caches.match(event.request) 
			.then(response => { 
				// Если ответ найден, выдаём его 
				if (response) { 
					return response; 
				} 

        const fetchRequest = event.request.clone(); 
		// В противном случае делаем запрос на сервер 
        return fetch(fetchRequest) 
          // Можно задавать дополнительные параметры запроса, если ответ вернулся некорректный. 
        .then(response => { 
			// Если что-то пошло не так, выдаём в основной поток результат, но не кладём его в кеш 
			if(!response || response.status !== 200 || response.type !== 'basic') { 
			  return response; 
			} 

			const responseToCache = response.clone(); 
			// Получаем доступ к кешу по CACHE_NAME 
			caches.open(CACHE_NAME) 
			.then(cache => { 
				// Записываем в кеш ответ, используя в качестве ключа запрос 
				cache.put(event.request, responseToCache); 
			}); 
			// Отдаём в основной поток ответ 
			return response; 
         } 
		); 
	}) 
  ); 
});

Для чего нужен метод clone у event.request и event.response?

Дело в том, что объект запроса и ответа — это поток, а поток может быть прочитан лишь единожды. Можете относиться к нему как к промису. Промис тоже всегда выполняется только раз.

Поэтому, если мы хотим использовать request для запроса и для записи в кеш, а response для ответа основному потоку и записи в кеш, — необходимо сделать клон соответствующей сущности.

Внимательно изучите код. Очень важно понимать каждый этап для самостоятельной работы с SW.

Напоследок разберём, для чего может понадобиться обработка стадии жизненного цикла activate. Активация происходит только после того, как предыдущая версия SW была удалена из браузера. Удалена версия, но кеш, который она оставила, может мешать (конфликтовать с актуальной версией кеша). В событии activate можно, например, очистить ненужный кеш:

this.addEventListener("activate", function(event) { 
	event.waitUntil( 
		caches.keys().then(cacheNames => { 
			return Promise.all( 
				cacheNames 
				.filter(name => {/* Нужно вернуть true, если хотите удалить этот файл из кеша совсем */}) 
        .map(name => caches.delete(name))  
      ) 
    }); 
  ); 
});

Сценариев использования кеширования много. Вы можете оптимизировать работу с сетью в вашем приложении, а можете добиться полноценной offline-версии. Отталкивайтесь от задачи и используйте доступные вам инструменты, о которых мы говорили выше. Дополнительные возможности вы сможете найти в полезных ссылках.
