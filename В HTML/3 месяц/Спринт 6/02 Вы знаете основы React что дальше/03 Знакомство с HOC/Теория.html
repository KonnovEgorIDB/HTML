Привет, HOC

HOC (от англ. High-Order Component, «компонент высшего порядка») — это удобный способ повторно использовать логику ваших компонентов.

Например, вы делаете онлайн-кинотеатр и хотите по нажатию на клавишу F разворачивать видео в полноэкранный режим (вызывать Fullscreen API). Для этого нужно подписаться на событие keyup.

Как это сделать? Напишем компонент:

export default class AdvVideo extends React.Component {
  private onKeyUp = (e: KeyboardEvent) => {
    if (e.key === 'f') {
      // Do business  
    }
  };

  public componentDidMount() {
    window.addEventListener("keyup", this.onKeyUp);
  }

  public componentWillUnmount() {
    window.removeEventListener("keyup", this.onKeyUp);
  }

  public render() {
    return <div />;
  }
}

Если вы сделали подписку в componentDidMount, не забудьте отписаться в componentWillUnmount. То же самое относится к выделению дополнительной памяти. Если вы выделили дополнительную память — убедитесь, что она не утекает.

Казалось бы, всё просто. Есть жизненный цикл, в нём можно делать всё, что захотим. Здесь появляются две проблемы:

  • Что делать, когда такая логика повторяется из компонента в компонент?
  • Что делать, когда такой логики очень много?

Ведь видео в сервисе может быть не одно: реклама, трейлеры, фильмы, и это реализовано разными компонентами.

Со временем компонент превратится во что-то такое:

export default class AdvVideo extends React.Component {
  private onKeyUp = (e: KeyboardEvent) => {
    if (e.key === 'f') {
      // Do business  
    }
  };

  // Ещё 400 строчек хендлеров и «помогаторов» логики 

  public componentDidMount() {
    window.addEventListener("keyup", this.onKeyUp);
    preloadSome();
    fetchData().then()....then().catch().then().......
    // Строчек 80 логики
    doSomeBusiness();
  }

  public componentWillUnmount() {
    window.removeEventListener("keyup", this.onKeyUp);
    // Наверняка в componentDidMount сделали что-то такое, что здесь забыли подчистить
  }

  // Это уже на 1421-й строчке кода, куда вы вряд ли долистаете
  public render() {
    return <div />;
  }
}

В результате он становится нечитаемым, сложным, слишком умным и крайне недекларативным.

Что хочется увидеть, открыв файл с JSX-разметкой? В первую очередь сам компонент — что он реализует и содержит, какую цель для бизнеса выполняет. Чаще всего взгляд первым делом обращается к следующим местам в коде:

  • Метод render — чтобы понять, какими данными оперирует компонент в отображении.
  • PropTypes или типизации state и props — чтобы охватить набор данных, доступных для использования.
  • Метод componentDidMount — чтобы понять, какие действия будут выполнены на старте жизненного цикла компонента. Возможно, там начнутся какие-то асинхронные запросы на получение данных.

Путешествие между этими точками в коде способно дать исчерпывающее представление о компоненте и его логике. А куда же поместить повторяющуюся логику? В компоненты высшего порядка, которые рассмотрим далее.

Как написать HOC

Создать компонент высшего порядка — не rocket science. Важно помнить, что Higher Order Components — не встроенный в React механизм, а просто концепция, реализуемая везде, где могут быть компоненты. HOC — это просто функция, которая принимает компонент и возвращает новый компонент.

Представьте, что вы работаете над крупным интернет-магазином, и вам поставили задачу — отображать часть баннеров и кнопки получения скидок только по выходным дням. Таких баннеров и кнопок в проекте много, все они разбросаны по файловой структуре, и надо придумать, как решить задачу элегантно.

Можно пойти наивным путем: изменить все нужные компоненты, вписав в них соответствующую логику. Во-первых, как показывает пример кода в предыдущем уроке, — это затратно. Можно легко запутаться, если нагружать одинаковой функциональностью множество разных компонентов — каким баннерам или кнопкам надо, каким не надо… А с изменением бизнес-требований придётся опять обходить все компоненты и вносить в них правки. Например, менеджер поставит задачу кроме выходных эти баннеры и кнопки надо показывать ещё по пятницам. Представляете себе эту боль — опять менять десятки компонентов?

Предлагаем решить эту задачу с помощью HOC.

Вспомним определение: компонент высшего порядка — это функция, которая принимает компонент и возвращает новый компонент. Начнём с заготовки, соответствующей определению:

function renderOnWeekends(WrappedComponent: React.ComponentType) {
  class NewComponent extends React.Component {
     // То ли ещё будет
  }

  return NewComponent;
};

Что здесь написано?

Во-первых, типы. Функция принимает компонент, у него есть тип ComponentType.

Во-вторых, внутри функции создаётся новый компонент. В данном случае классовый компонент. Обязательно ли делать именно классовый компонент? Нет, можете также сделать функциональный.

Переименуем создаваемый компонент для чистоты кода и добавим логики:

function renderOnWeekends(WrappedComponent: React.ComponentType) {
  class OnWeekendComponent extends React.Component {
		private isWeekend = false;

		constructor(props) {
			super(props);
			const currentDay = new Date().getDay();
			this.isWeekend = [6, 7].includes(currentDay);
		}

    public render() {
      return this.isWeekend ? <WrappedComponent {...this.props} /> : null;
    }
  }

  return OnWeekendComponent;
}

Что добавилось?

Во-первых, появился конструктор нового компонента, где происходит расчёт бизнес-логики, в нашем случае — определение выходного дня. Почему в конструкторе и почему значение храним в экземпляре, а не в state? Потому что это простая логика, которую достаточно посчитать один раз, и после этого она не изменяется. Конструктор является идеальным местом для этого — он будет вызван раньше всех, всё посчитает, и компонент к моменту отрисовки будет владеть нужной информацией.

Во-вторых, добавился render, в котором учитывается результат работы бизнес-логики: если посчитано, что день выходной — будет отрисован оборачиваемый компонент; если нет — ничего.

В третьих, происходит проброс props в оборачиваемый компонент. Компонент OnWeekendComponent должен принимать ровно те же пропсы, что и оборачиваемый компонент. Нужно это для того, чтобы передать ему эти пропсы. Это важно — в коде мы будем использовать созданный HOC-ом компонент так же, как оригинальный. Поэтому HOC должен уметь принимать всё те же входные данные, что и оригинальный компонент. Может ли HOC иметь или пробрасывать дополнительные пропсы? Да, об этом в следующем уроке.

Важно помнить смысл совершенных действий: убрать дублирование и сделать бизнес-компоненты более читаемыми, переместив лишнюю логику (в нашем случае расчёт выходного дня) в компоненты высшего порядка.

На этом можно сказать, что базовая версия HOC для отображения компонентов по выходным дням готова. Посмотрим, как использовать этот HOC:

function Banner1() { ... }  // этот баннер показывать только по выходным
function Banner2() { ... }
function SaleButton1() { ... } // эту кнопку показывать только по выходным
function SaleButton2() { ... }

const WeekendBanner1 = renderOnWeekends(Banner1);
const WeekendSaleButton1 = renderOnWeekends(SaleButton1);

// Теперь в разметке надо применять обёрнутые в HOC компоненты:
function App() {
	return <div>
		<WeekendBanner1 /> {/* будет показан только в выходные */}
	</div>
}

Но будьте уверены, менеджеры на этом не остановятся. :) Например, они захотят ещё:

  • Чтобы определённые баннеры показывались по понедельникам.
  • Поэкспериментировать с кнопкой на главной странице и посмотреть, по каким дням она поднимает конверсию.

Эти задачи будут решены в следующем уроке.
