React и безопасность

Что это такое и как вредит пользователям, обсуждали в прошлом модуле. Освежить в памяти поможет статья на Хабре или соответствующий урок.

Поговорим про данную уязвимость в React.

Из «коробки» React умеет защищать и экранировать контент. Если встречаются уязвимые символы (' например), он предлагает обернуть их в {}:

<span>{'\'ПРИВЕТ\''}</span>

Server Side

В следующих уроках вы узнаете про Server Side Rendering подробнее. Здесь воспользуемся небольшим куском кода:

<script>window.__STATE__ = ${JSON.stringify({ data })}</script>

В примере выше серверный рендеринг собирает все начальные данные для Redux-хранилища. Вы отправляете предзапросы в бэкенд и добавляете их в хранилище на NodeJS или делаете ещё какие-либо манипуляции с Redux-стором.

Чтобы прокидывать данные с сервера на клиент, обычно используют такой приём:

const renderNodejsExpressRoute = (req, res) => {
  res.send(`<html>...<script>window.__STATE__ = ${JSON.stringify({ data })}</script></html>`);
};

Таким образом, клиент получит данные и будет иметь доступ к window.__STATE__ (можете придумать другое название для переменной). Дальше из этого __STATE__ вы уже пробрасываете данные в хранилище клиента и удаляете эту переменную, чтобы не плодить лишние данные.

Теперь рассмотрим пример с точки зрения безопасности. Если data будет содержать что-то такое:

{ xss: "</script><script>alert('Bad boy, bad boy, ... song')</script>" }

Поскольку мы отправляем всё тот же обычный документ, нет ничего, что препятствует исполнению кода злоумышленника.

Защититься от этого поможет дополнительный метод. Его можно установить из npm:

~$ npm install --save serialize-javascript

Пример использования:

<script>window.__STATE__ = ${serialize(data, {isJSON: true})}</script>

Сработает даже без последнего аргумента ({isJSON: true}).

Вставляем контент опасно

В документации ReactJS у компонента есть интересное свойство: dangerouslySetInnerHTML.

Пример:

function MyComponent() {
  return <div dangerouslySetInnerHTML={{__html: 'First &middot; Second'}}/>;
}

Вы можете вставлять любые теги и контент в обход React.

Важно: не используйте это свойство, если сомневаетесь, что оно вам нужно или есть альтернативы.

В каких случаях оно действительно нужно?

Например, вы делаете CMS для вашего приложения, где хотите динамически менять контент, картинки и т. д. Есть специальная админка (допустим, написанная вами) с системой WYSIWYG. Ваши менеджеры или заказчики хотят сами менять текст и не напрягать разработку. Естественно, они хотят делать красивые тексты (например, добавлять стили, жирность шрифта, цвет текста). Как хранить это в базе? Один из вариантов — в Markdown, но чаще это делают в HTML. Например, вот так:

const SOME_MANAGER_DATA = '<span>Мой <span style="color: red; font-weight: bold">очень</span> красивый текст</span>';

function MyComponent() {
  return <div dangerouslySetInnerHTML={{__html: SOME_MANAGER_DATA}}/>;
}

Разобрались, зачем это нужно, перейдём к мерам защиты. Во-первых, сами экранируйте все значения из бэкенда — не доверяйте никому (даже своему бэкенду и тем более бэкендерам). Во-вторых, старайтесь использовать приёмы вроде dangerouslySetInnerHTML как можно реже. Если можно заменить или обойтись без него — действуйте. В-третьих, используйте сканеры XSS, отдавайте на аудит группе СИБ (специалистов информационной безопасности). Если у вас такие есть, конечно. Если нет, а проект коммерческий с большим числом пользователей, постарайтесь убедить руководство привлечь сторонних аудиторов для анализа всей системы. Это принесёт большую пользу.

CSP (Content Security Policy)

Ниже вы найдете ссылки на несколько полезных инструментов, которые помогут вам подключить CSP к проекту.

CSR (Client Side Rendering)

Но в начале покажем способ для работы со статикой и Webpack. С клиентским рендерингом вы можете устроить CSP с помощью nginx. Если нужно, заводите дополнительный Webpack-плагин.

Webpack-плагин

CSP HTML Webpack Plugin — поможет подключить к вашей статике CSP-политики через конфиги.

Nginx

Пример политик CSP на nginx можете посмотреть GitHub, а здесь статья о том, как их подключить. Обратите также внимание на эту статью на Хабре, где, помимо прочего, найдёте ещё один пример политики.

SSR (Server Side Rendering)

Пример библиотеки с хорошей сигнатурой (API) — express-csp-header. Попробуйте её, а если чувствуете в себе силы, напишите свое решение. Исходники относительно простые.

Один из способов организации дефолтных правил — собрать их в одном файле, а потом перезаписывать для production и testing среды:

// /../production.ts

const defaultConfig = require('./defaults');

module.exports = {
    csp: {
        policies: {
            ...defaultConfig.csp.policies,
            'img-src': [
                ...defaultConfig.csp.policies['img-src'],
                'avatars.my.app',
                'https://may-app.tst.domain.tv'
            ],
            'connect-src': [...defaultConfig.csp.policies['connect-src'], 'https://sentry.my.app.ru'],
            'frame-src': [...defaultConfig.csp.policies['frame-src'], '*.myapp.ru', '*.myapp.com'],
            'frame-ancestors': [...defaultConfig.csp.policies['frame-ancestors'], '*.myapp.com']
        }
    }
};
