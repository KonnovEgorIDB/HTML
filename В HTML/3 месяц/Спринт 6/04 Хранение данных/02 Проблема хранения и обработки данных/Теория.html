Проблема хранения и обработки данных

Итак, контексты не очень подходят, подумаем над другим решением.

Контексты давали весомый бонус — каждый контекст существует в единственном экземпляре где-то наверху приложения, и те, кому надо, имеют к нему доступ. Это похоже на паттерн «Синглтон», и это хорошая идея, которую стоит взять на заметку.

Хоть мы и используем React, никто не запрещает нам сделать отдельный модуль, поместить в него какой-то код и использовать везде, где нужно, импортируя этот модуль:

// storage.ts

// Какой-то объект с данными
export const store = {
	language: 'RU',
	curency: 'RUB'
};

// Header.tsx
import { store } from 'app/storage.ts'

// Footer.tsx
import { store } from 'app/storage.ts'

Мы легко получаем доступ к переменной и можем её использовать в разных компонентах. Но сейчас эта переменная только для чтения — React никак не отреагирует на изменения в объекте store.

Прежде чем начать писать велосипеды для подписки на обновления store, вспомним MVC и познакомимся с архитектурным подходом «однонаправленный поток данных», он же “unidirectional data flow”.

Как было в MVC? Контроллер работал с моделью и отображением. Отображение передавало действия пользователя в контроллер, тот реагировал, работал с моделью и обновлял отображение. Так же модель могла сообщить о своих изменениях контроллеру, и тот опять обновлял отображение. А если MVC «приготовить» неправильно, тогда может получиться так, что модель работает напрямую с отображением или отображение с моделью. Связи между сущностями направлены в разные стороны, это непросто понимать и отлаживать.

Альтернативой MVC служит архитектурный подход однонаправленного потока данных, и одной из его разновидностей является Flux — подход, предложенный разработчиками из Facebook. Прежде всего посмотрим, из каких частей состоит Flux:

  • Представления — компоненты, которые занимаются отображением данных из хранилища и реакцией на действия пользователя. Представления порождают Действия.
  • Действие — единица информации, подобная событию, которая содержит информацию о названии действия и какие-то нужные данные. Обычно действия — это просто объекты: { type: 'CHANGE_LANGUAGE', payload: { newLanguage: 'EN' } }. Действия передаются Диспетчеру.
  • Диспетчер — сущность, которая совершает только одно действие — передаёт события в хранилище.
  • Хранилище — объект, который хранит данные и обрабатывает действия. Когда в хранилище приходит действие, хранилище знает, как его обработать и как изменить свои данные. После того как хранилище обновит свои данные, об этом узнают Представления и нарисуют новую информацию (или нет, если информация не изменилась).

Цепочка замкнулась. Представление → Действия → Диспетчер → Хранилище → Представление → … Однонаправленность очень понятна и упрощает отладку — ничего не происходит без причины, а причиной всегда является действие.

Flux — это одна из реализаций однонаправленного потока данных. Бывают другие подходы, в которых может быть больше частей, например: мидлвари, редьюсеры, создатели действий.

Теоретической информации достаточно, можно приступать к построению велосипеда на однонаправленном потоке данных. Создадим простейшую реализацию Flux-подхода и используем в компонентах Header и Footer абстрактного интернет-магазина.

// storage.ts

// Тип для действия
type TAction = {
	name: string;
	payload?: any;
}

// Хранилище и диспетчер объединим в один класс и инкапсулируем в нём всю логику
class FluxStorage<TData> {
	// Здесь будут храниться данные приложения.
	// Предзаполним их
	private data: TData = {
		language: 'RU',
		currency: 'RUB'
	};

	// Здесь будем хранить функции оповещения из отображений
	private listeners: Array<(data: TData) => void> = [];

	// Диспетчер
	// Этот метод будет вызываться компонентами-представлениями
	// Сюда они будут передавать действие
	dispatch(action: TAction): void {
		this.processAction(action);
	}

	// Этот метод синтетический, чтобы показать что он не диспетчер, а именно обработчик действий
	// Всё происходящее в этом методе можно было разместить в dispatch.
	private processAction(action: TAction): void {
		//  Научимся реагировать на нужные действия
		switch(action.name) {
			case 'CHANGE_LANGUAGE': {
				const { newLanguage } = action.payload;
				this.data = { ...this.data, language: newLanguage };
				break;
			}
			case 'CHANGE_CURRENCY': {
				const { newCurrency } = action.payload;
				this.data = { ...this.data, currency: newCurrency };
				break;
			}
		}
		// Изменение данных закончили, надо оповестить отображения
		this.emitUpdates();
	}

	// Метод оповестит подписанные отображения
	private emitUpdates(): void {
		// Пройдём по всем подпискам и оповестим их новыми данными
		this.listeners.forEach(listener => listener(this.data));
	}

	// Дадим отображениям подписываться на обновление данных
	subscribe(listener: (data: TData) => void): VoidFn {
		this.listeners.push(listener);
		// Сразу отправим отображению актуальные данные
		listener(this.data);
		// Вернём функию для отписки, ведь когда отображение отмонтируется — ему не нужны будут оповещения
		return () => {
			this.listeners = this.listeners.filter(l => l !== listener);
		}
	}
	
}

export type TOnlineShopData = {
	language: string;
	currency: string;
}

// Предоставляем экземпляр всем желающим импортировать его из модуля
export const store = new FluxStorage<TOnlineShopData>();

Отлично! Механизм создан. Не самый гибкий на текущий момент, но надёжный, как швейцарские часы. Применим его:

// Header.tsx
import React, { useState, useEffect } from 'react';
import { store, TOnlineShopData } from 'app/storage';

function Header() {
	// Обратите внимание — начального языка тут нет
	// Он будет получен из хранилища при подписке
  const [language, setLanguage] = useState("");
  useEffect(() => {
    const subscription = store.subscribe((data) => {
      const { language } = data;
      setLanguage(language);
    });

    return subscription;
  }, []);

  function handleChangeLanguage(e) {
    const newLanguage = e.target.value;
    store.dispatch({ name: 'CHANGE_LANGUAGE', payload: { newLanguage } });
  }

  return (
    <div className="header">
      <select onChange={handleChangeLanguage} value={language}>
        <option value="RU">Ru</option>
        <option value="EN">En</option>
        <option value="EST">Est</option>
      </select>
    </div>
  );
}

Попробуйте этот код, например в codesandbox.io. Несколько раз добавьте в разметку компонент Header и убедитесь, что смена языка в одном компоненте вызовет смену языка в другом.

Вот так просто реализуется то, что называется «стейт-менеджер». Здесь ещё есть что улучшить:

  • Выделить так называемые action creator-ы, функции, позволяющие вместо { name: 'CHANGE_LANGUAGE', payload: { newLanguage } } писать makeChangeLanguageAction(newLanguage) — при большом количестве действий это сократит код и сделает его более осмысленным.
  • Организовать подписку на изменения данных не в самом компоненте, а сделать для этого HOC или hook.
  • Обучить FluxStorage работать не с «захардкоженными» обработчиками (то есть написанными в коде самого класса), а с произвольными. Говоря иначе — сделать возможность без изменения самого FluxStorage добавлять действия и обработчики для них.

Схема однонаправленного потока данных мощная и открывает большое количество возможностей. Она позволяет избегать спагетти-логики. Но к ней есть много вопросов, с которыми разберёмся по ходу темы. Например:

  • Как работать с асинхронными данными?
  • Если все подряд будут ссылаться на эти данные, везде будет происходить перерендер?
  • Много ли своих велосипедов надо написать?
  • Как правильно хранить данные?
  • Когда использовать state компонента, а когда store-хранилища?
