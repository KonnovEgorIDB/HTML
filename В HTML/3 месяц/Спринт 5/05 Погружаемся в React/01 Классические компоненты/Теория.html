Классические компоненты

В React нет собственных компонентов — их нужно создавать самостоятельно. Есть два типа компонентов:

  • Примитивные — это кнопки, поля ввода, ссылки, иконки, изображения, радиокнопки, чекбоксы.
  • Сложные — сообщение об ошибке с текстом и кнопками или форма с несколькими полями.

И примитивные, и сложные компоненты переиспользуются. Поэтому к их созданию следует подходить серьёзно. Важно знать, как они устроены и как их правильно создавать.

Создать переиспользуемый компонент можно двумя способами: в виде функции и как класс. Подробно это описано в документации, но не спешите открывать ссылку. Ниже разберём примеры.

Самый простой способ — это создание компонента в виде функции. Про него расскажем в следующем уроке, так как пусть он и простой, но имеет некоторые тонкости:

function Welcome(props) {
  return <h1>Hello, {props.name}</h1>;
}

Здесь же обсудим классические компоненты, которые создаются с помощью ES6-классов через наследование:

class Welcome extends React.Component {
  render() {
    return <h1>Hello, {this.props.name}</h1>;
  }
}

Добавляем компонент на страницу:

const element = <Welcome name="Алиса"/>;

ReactDOM.render(
  element,
  document.getElementById('root')
);

Заметим, что первым аргументом функции render можно отправлять как константу, так и JSX-код.

Для компонентов в React свойственна композиция, то есть внутри одного компонента можно комбинировать другие компоненты. И так рекурсивно.

Компоненты стараются переиспользовать. Пример:

function App() {
  return (
    <div>
      <Welcome name="Алиса"/>
      <Welcome name="Базилио"/>
      <Welcome name="Буратино"/>
    </div>
  );
}

ReactDOM.render(
  <App/>,
  document.getElementById('root')
);

Избегайте наследования компонентов. Этот паттерн плох, так как не ложится на схему компонентного подхода. Компонент должен быть уникальным и унифицированным. Всё остальное — это композиция других компонентов. Подробнее про это можно почитать в документации.

Если хотите, чтобы дочерние компоненты попали на страницу на том же уровне в DOM, используйте фрагменты — <React.Fragment> или просто <>:

function App() {
	// Можно и так: <React.Fragment>...</React.Fragment>

  return (
    <>
      <Welcome name="Алиса"/>
      <Welcome name="Базилио"/>
      <Welcome name="Буратино"/>
    </>
  );
}

ReactDOM.render(
  <App/>,
  document.getElementById('root')
);

Такой подход позволяет не оборачивать в лишние div или другие теги и не «раздувать» DOM-дерево.

Не бойтесь декомпозировать компоненты на более мелкие. Особенно те части, которые собираетесь переиспользовать. Более детально об этом в документации.

Про жизненный цикл вам предстоит прочитать самим вот здесь. Но мы не просто отпускаем вас на сторонний источник. Уроки будут рассказывать не самые очевидные вещи, которых может и не быть в документации.

Например, рассмотрим отличие PureComponent от Component.

Для этого вспомним какой жизненный цикл у компонента (подробнее, как его реализовать, посмотрите по ссылке выше). Основные методы такие:

  • constructor — не стесняйтесь инициализировать необходимые данные в конструкторе или при создании класса;
  • componentDidMount — запускается после того, как компонент отрендерился в DOM;
  • componentWillUnmount — запустится перед тем, как компонент будет удалён из DOM-дерева;
  • componentDidUpdate — будет вызван сразу после обновления компонента (изменились пропсы). Важно: не будет вызван при первом рендере, используйте componentDidMount;
  • shouldComponentUpdate — будет вызван перед рендером, когда получит новые пропсы и состояние. По умолчанию в Component-классах стоит true;
  • componentDidCatch — будет вызван после возникновения ошибки у компонента-потомка.

Диаграмму жизненного цикла компонента можно увидеть здесь.

Вернёмся к сравнению Component и PureComponent.

При использовании Component по умолчанию происходит повторный рендер при любом изменении состояния.

Запустите у себя вот такие компоненты и попробуйте понажимать на кнопки (не бойтесь state, про него поговорим дальше):

import React, { Component } from "react";
import { render } from "react-dom";

class MySuperComponent extends Component {
  render() {
    const { name } = this.props;
    console.log(`Имя: ${name}`);

    return <h1>{message}</h1>;
  }
}

export default class App extends Component {
  state = {
    name: "Пупа",
    dummy: false
  };

  toggleMessage = () => {
    const { name } = this.state;

    this.setState({ name: name === "Пупа" ? "Лупа" : "Пупа" });
  };

  toggleDummy = () => {
    this.setState({ dummy: !this.state.dummy });
  };

  render() {
    const { name } = this.state;

    console.log("Рендер App");

    return (
      <React.Fragment>
        <MySuperComponent name={name}/>

        <button onClick={this.toggleMessage}>Изменить сообщение</button>
        <button onClick={this.toggleDummy}>Сделать пустое изменение</button>
      </React.Fragment>
    );
  }
}

const rootElement = document.getElementById("root");
render(<App/>, rootElement);

Суть примера в том, что компонент не зависит от dummy-свойства, но даже при изменении этого свойства мы получаем лишний перерендер компонента MySuperComponent.

Это происходит потому, что shouldComponentUpdate всегда возвращает true у компонента, который наследуется от Component.

Данный метод нужен для повышения производительности, однако не старайтесь сами его использовать просто так. «Поиграться» и попробовать — однозначно да, но не нужно делать жизнь сложнее, к тому же с потенциальными ошибками. Процитируем авторов ReactJS:

Вместо этого используйте PureComponent, который позволяет не описывать поведение shouldComponentUpdate() вручную. PureComponent поверхностно сравнивает пропсы и состояние и позволяет не пропустить необходимое обновление.

Именно по этой причине, если вы хотите сделать лишние перерендеры или нужно из shouldComponentUpdate возвращать true, — используйте наследование от Component. В остальных случаях — PureComponent к вашим услугам. Он позволит уменьшить число ненужных переотрисовок.

Небольшой оффтоп. Зачем и кому сдались эти переотрисовки? Ну отрисуется большее число раз и что в этом такого?

Да, когда на странице одна кнопка и текст “Hello, World” — это одно.

Другое дело, когда ваше приложение — это рекурсивная композиция сложных компонентов, которые производят местами простую, местами нетривиальную логику. В таком случае незачем лишний раз заставлять компьютер пользователя «свистеть» и «кряхтеть». Это ещё не самое худшее. Проблемы начнутся, когда у пользователя интерфейс будет ещё и медленно работать. А количество бесполезных переотрисовок со сложными анимациями и утилитами в этом только помогут.
